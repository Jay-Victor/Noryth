# 05 · 路线图、验收门禁与风险

---

## 1. 分期总览

原则：**每一期都以"能跑通一个真实动作"为终点，不以"写完了某个模块"为终点。**
工期是单人全职的估计区间（下限=顺利，上限=踩坑），不是承诺。

| 期 | 主题 | 工期 | 终点动作 |
|---|---|---|---|
| **P0** | 骨架与数据模型 | 1.5–2 周 | `noryth init` 建出可提交的项目 |
| **P1** | 剧场内核 | 2.5–3.5 周 | CLI 跑完一场 40 拍，可回退 |
| **P2** | 记忆与一致性 | 2.5–3.5 周 | 角色不再说漏，设定锁生效 |
| **P3** | 六类 Agent 与正文 | 3.5–4.5 周 | 一场戏 → 一章稿 → 审出问题 → 改一版 |
| **P4** | TUI | 1–1.5 周 | 不用鼠标跑完 20 拍 |
| **P5** | Desktop GUI | 4–6 周 | 三条主路径可点通 |
| **P6** | 打磨与打包 | 2–3 周 | 可交给一个陌生人安装使用 |

合计 **17.5–24 周**。可以并行的地方只有 P4 与 P5 的骨架，其余是串行依赖。

## 2. 各期交付物与验收门禁

**实施状态**：P0、P1 已完成。P0 的三平台 Electron / `better-sqlite3` 原生模块验证延后到 P6 打包前；P2 未开始。

### P0 · 骨架与数据模型

**交付**：monorepo（pnpm workspaces）、`@noryth/core` 领域类型、`02-schema.sql` + 迁移器、命令总线（幂等收据）、`noryth init / open / status`、Git 初始化与首次提交。

**门禁**（全部机器可判）：

| # | 门禁 | 判定方式 |
|---|---|---|
| 1 | schema 在真引擎建库，73 条约束断言全过 | `python scripts/check.py --schema` |
| 2 | 参数表与代码零漂移 | `python scripts/check.py --params` |
| 3 | `noryth init` 在空目录建出 7 个文件/目录，二次执行不破坏 | 脚本断言目录树 |
| 4 | 同一命令重放两次只产生一条消息 | 插入幂等键，断言 `count(*)=1` |
| 5 | 事件日志 UPDATE/DELETE 被拒 | 断言 `IntegrityError` 含 `ck_event_immutable` |
| 6 | 提交后 `git log` 有 1 条，含 `Noryth-Checkpoint` | `git log --format=%B` |

**不做**：任何模型调用。P0 必须能在完全离线、没有任何 API key 的情况下跑完门禁。

**状态**：已完成（6/6）。三平台 Electron 最小壳 + 原生模块验证延后到 P6 打包前，见 §3.2。

### P1 · 剧场内核

**交付**：调度器（评分/阻尼/硬上限/仲裁）、上下文装配（配额+降级）、知识边界（`cognition` + 前置过滤）、导演（事件卡/升级阶梯/收束求值）、3 角色 + 1 旁白、`noryth run --scene <id>`、检查点与回退、`noryth commit`、Git 状态包与 `restore --from-commit`。

**门禁**：

| # | 门禁 | 阈值 | 判定 |
|---|---|---|---|
| 1 | 500 拍仿真最长连任 | ≤ 3 | `noryth_proto.py --demo` |
| 2 | 单人最高占比 | ≤ 40% | 同上 |
| 3 | 旁白占比 | 15%–25% | 同上 |
| 4 | 仲裁触发率 | ≤ 18% | 同上 |
| 5 | 装配上下文 | ≤ 预算，且不截断半句 | 断言 `tokens ≤ budget` |
| 6 | 越权事实进入提示词 | **0 条**（72 次装配累计） | 探针 |
| 7 | 40 拍场景端到端 | 跑通，且 exit 或 WARN 二者之一 | CLI 退出码 + 事件 |
| 8 | 回退 8 域逐域计数 | 每域回到目标 seq 的值 | 逐表对比断言 |
| 9 | 回退后重放一致 | 同 seed 同上下文产生同一 beat 序列 | 两次运行 hash 相等 |
| 10 | 到 `max_beats` 未收束 | 写 `WARN exit_conditions_unsatisfied`，不静默截断 | 事件断言 |
| 11 | 闪回不触发时间线错误 | 同 timeline 倒退被拒、换 timeline 通过 | `ck_scene_time_regression` |
| 12 | 跨章认知快照 | 审第 3 章时看不到第 20 章才有的认知 | `v_knowledge_by_chapter` |

**这一期的三个陷阱**（写在这里，因为最容易在这里返工）：

1. **旁白靠权重竞争会拿不到发言权**（实测 0%）。节奏必须是硬约束。
2. **仲裁的平局判定不能把被钳制到 0 的候选算进去**，否则每拍都触发。
3. **回退必须逐域验证**。少退一个域不报错，只在下一轮表现为"角色说漏"。

**状态**：已完成（12/12 路线图门禁）。额外两条端到端门禁也已通过：`restore --from-commit` 删库恢复、`noryth commit` 未关闭场景恢复并继续跑；`pnpm gate:p1` 14/14。

### P2 · 记忆与一致性

**交付**：事实库（三态+槽位）、认知与感知、关系轴、设定锁、五类冲突检测、场景摘要、检索（加权 RRF + 绝对刻度 + MMR）、嵌入管线（可插拔，本地/远程）、后台任务（`job` + generation）。

**门禁**：

| # | 门禁 | 阈值 |
|---|---|---|
| 1 | 陈旧值泄漏（回退后仍被引用） | **0** |
| 2 | 结构化断言越权 | **0** |
| 3 | 设定锁：换 ID 写同槽位 | 100% 拦截 |
| 4 | 物品唯一持有 | 100% 拦截（单值槽位） |
| 5 | 关系突变未给理由 | 100% 钳制 |
| 6 | 检索 recall@8（词面可解集） | ≥ 85% |
| 7 | 无关查询 precision@3 | ≥ 90% |
| 8 | 检索 p50 @ 5 万节点 | ≤ 100 ms |
| 9 | 摘要可回溯 | 删除有子节点的记忆被拒 |

**探针集要求**：≥ 50 个节点、七类覆盖（陈旧值 / 纠正 / 连续性 / 聚合 / 常驻通道 / 无关精度 / 改写问法），**70/30 切 dev/held-out**，held-out 只在发布前跑一次并在报告里声明污染情况。

**已知缺口单列、不进门禁**：跨措辞召回（同一事实换说法）依赖嵌入模型能力，hash 占位嵌入下必然失败。把它算进 PASS 是自欺，算进门禁会让门禁永远红着。

### P3 · 六类 Agent 与正文

**交付**：规划/写作/修订/审批四类 Agent 的契约与实现、章节文件与 outbox、revision 链、issue 生命周期、审批→修订直连（默认关）、Markdown 渲染与 diff。

**门禁**：

| # | 门禁 | 阈值 |
|---|---|---|
| 1 | 一场戏 → 一章稿 | 跑通，`facts_used` 覆盖被引用的全部事实 |
| 2 | 写作 Agent 新增事实 | **0 条**（抽取比对） |
| 3 | 修订输出挂不上 issue 的修改 | **0 条** |
| 4 | 审批 issue 附证据率 | ≥ 80% |
| 5 | 审批阻塞级误报率 | ≤ 20%（人工抽样 30 条） |
| 6 | 直连轮次上限 | 3 轮后强制交还作者 |
| 7 | 外部编辑冲突 | 不覆盖，走三选一对话框 |
| 8 | `git diff` 可读 | 行级、按章节分组 |
| 9 | 章节 ↔ 场景映射 | 一章挂多场，写作 Agent 按 `ord` 取到正确顺序 |
| 10 | 重写的三种语义 | 开分支 / 仅替换（后续标 `stale`）/ 重跑，三者行为可断言 |
| 11 | 导入幂等 | 同一份稿导入两次，实体与事实数量不变 |

**这一期最容易被低估的是"审批"**。它不是"再问一次模型对不对"，而是**检索 + 比对**：把正文里的每条断言拿出来，反查 `fact`（truth=1？）、`cognition`（此角色知道吗？）、`relation`（态度一致吗？）。没有检索的审批 Agent 只会输出"文笔流畅，情节合理"。

## 3. 测试与 CI

没有这一节，前面所有门禁都只是"应该会过"。

### 3.1 四层测试

| 层 | 测什么 | 放哪 | 门槛 |
|---|---|---|---|
| **契约** | schema 约束、参数↔代码、视图语义 | `scripts/check.py` | 73 条断言全过（已存在） |
| **纯函数** | 评分 / 装配 / 限知 / 收束求值 / 声音距离 | `packages/core/**/*.test.ts` | 行覆盖 ≥ 90%，分支 ≥ 80% |
| **集成** | 命令总线 + SQLite + outbox + Git | `packages/store/test/` | 每条写入路径三例：成功、幂等重放、失败回滚 |
| **端到端** | 新建 → 10 拍 → 回退 → 重跑 → 成章 → 审 → 修 → 提交 | Playwright（P5 起） | 3 条主路径，每次发版跑 |

**黄金场景回归**（最值钱的一个）：固定 seed + 固定 stub 模型（返回预置 JSON），跑 40 拍，把 `beat` 序列、越权计数、装配 token 数存成 baseline。任何改动让这三个数变了，CI 必须解释为什么。

它防的不是"代码坏了"，是"行为悄悄变了"——调一个权重、改一句提示词，输出就会漂，而所有单元测试依然全绿。

### 3.2 CI 矩阵

| 任务 | 平台 | 何时跑 | 目标耗时 |
|---|---|---|---|
| `check.py`（契约） | ubuntu | 每次 push | < 10 s |
| core 单测 | 三平台 | 每次 push | < 60 s |
| Electron 最小壳 + `better-sqlite3` require | win / mac / linux | 打包前（P6）+ 发版前 | < 8 min |
| 黄金场景回归 | ubuntu | 每日 + 发版前 | < 5 min |
| 打包产物冒烟（安装→打开→新建项目） | 三平台 | 发版前 | < 20 min |

三平台原生模块验证延后到 P6 打包前跑一次（P0/P1 先在 Windows 上验证）。`electron-rebuild` 失败必须在上架前暴露，不能拖到发布当天。

### 3.3 交互 SLO（写进性能预算，不是"感觉卡"）

| 交互 | 目标 p95 | 超了怎么办 |
|---|---|---|
| 切换场景 | < 100 ms | 消息列表虚拟化 + 按 scene 预取 |
| 打开 10 万字章节 | < 500 ms | CodeMirror 非受控 + 分段渲染 |
| 单拍首 token | < 2.5 s | 流式输出 + 超时换模型 |
| 完整一拍（40 拍场景内） | < 8 s | 摘要/嵌入并发，别串行 |
| 回退影响预览 | < 200 ms | 8 域计数走索引，不扫全表 |
| 检索（5 万节点） | < 100 ms | 已实测 6.5 ms，留 15× 余量 |

**首 token 与完整一拍必须分开计**：用户感知的是"开始有字"的时间，不是结束时间。合成一个指标，就会为了总时长去牺牲流式体验。

## 4. 风险表

按"发生概率 × 影响"排序。每条给触发信号——**没有触发信号的风险等于没写**。

| # | 风险 | 概率 | 影响 | 触发信号 | 缓解 |
|---|---|---|---|---|---|
| 1 | **中文文风在 JSON 里退化**（角色拍强制 JSON，句子变干） | 高 | 高 | 抽样 20 拍，人工评分比自由文本低 > 1 分 | 角色拍字段短（1–4 句），JSON 影响有限；保留"先写散文再抽结构"的开关作为退路 |
| 2 | **知识越界抽取器误报高** | 高 | 中 | 告警里人工判定为真的 < 60% | 抽取只告警不阻断；结构化断言才是门禁 |
| 3 | **成本失控** | 中 | 高 | 单章成本 > 5 元 | 三档模型（主持人贵/角色中/摘要便宜）+ 每项目预算上限 + 摘要批量 |
| 4 | **场景跑飞**（40 拍没推进） | 中 | 高 | `WARN exit_conditions_unsatisfied` 占比 > 20% | 事件卡 + 升级阶梯 + 收束条件；每场强制设目标 |
| 5 | **MinGit 在 macOS/Linux 无便携包** | 高 | 中 | 目标平台无 git 或版本 < 2.30 | 降级为"仅检查点版本控制"并明确提示；文档写清 |
| 6 | **better-sqlite3 原生模块打包失败** | 中 | 高 | `electron-rebuild` 后 require 失败 | P6 打包前在三平台 CI 上跑一次最小 Electron 壳，不要等到发布当天 |
| 7 | **回退后重放不一致**（同一 seed 不同结果） | 中 | 高 | 两分支同上下文 beat 序列不同 | jitter 用确定性哈希；模型温度固定；记录 `model + prompt_hash` |
| 8 | **用户不信任自动生成** | 中 | 中 | 用户 90% 的拍都是手动改 | 默认单步；"为什么是它"必须可解释；拦截/放行可显式覆盖 |
| 9 | **大章节卡顿** | 低 | 中 | 10 万字章节输入延迟 > 50 ms | CodeMirror 6 非受控；对话流虚拟化 |
| 10 | **schema 迁移失败** | 低 | 致命 | 升级后打开旧项目报错 | 每次迁移先 `VACUUM INTO` 备份；迁移前自动建检查点 |
| 11 | **模型 JSON 能力不稳定** | 中 | 中 | `bad_json` > 5% | 重试 1 次带错误位置；兜底取 `line` 字段；必要时换模型 |
| 12 | **用户用网盘同步项目文件夹** | 中 | 高 | `.noryth/*.db-wal` 冲突文件出现 | 启动时检测同步盘路径（OneDrive/Dropbox/iCloud），警告并建议关闭实时同步 |

第 12 条不是玩笑：SQLite + WAL + 云盘同步是已知的数据损坏组合。**必须主动检测并警告**，否则用户会在某天发现三章稿没了。

## 5. 成本

基于探针实测的 token 量（占位价 2 元 / 8 元每百万 token）：

| 项 | 数值 |
|---|---|
| 每场 40 拍 | 43 次调用，191,080 tok |
| 每场成本 | 0.452 元 |
| 120 场（约 30 万字） | 22.9 M tok，**54.2 元** |

价格是占位符。真实的三个变量：
1. **供应商单价**（差 10 倍很常见）
2. **缓存命中率**（system 段稳定 → 前缀缓存能省 50–90% 的输入 token）
3. **重试率**（JSON 失败、越界重写）

护栏：设置页有"每项目预算上限"，到 80% 弹提示，到 100% 停止自动生成（仍可手动单步）。

## 6. 如果只能做一半

按这个顺序砍，砍到哪都能用：

1. 剧场内核（P1）——**不能砍**，砍了就没有产品
2. 知识边界（P2 的一半）——**不能砍**，砍了只能写短篇
3. 回退（P1 的一部分）——**不能砍**，砍了用户不敢用
4. 写作 + 审批（P3 的一半）——可以晚，但要有"导出到 Markdown 手动改"的退路
5. GUI（P5）——可以先只做 TUI + 导出，但 GUI 是"给别人用"的门槛
6. 规划 Agent（P3）——可以先用 Markdown 手写设定
7. 修订 Agent（P3）——可以先用外部编辑器
8. TUI（P4）——纯锦上添花
9. 事件卡（P1 的一部分）——没有它也能跑，只是戏会平

## 7. 里程碑检查点（自用）

每个里程碑问三个问题，答不上就不算过：

1. **它能跑一个真实动作吗？**（不是"模块写完了"）
2. **这个动作的数字是什么？**（拍数、越权数、延迟、成本）
3. **如果明天换一个模型供应商，要改几行？**（> 20 行说明抽象漏了）
