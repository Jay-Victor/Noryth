# 03 · Agent 体系、调度与记忆

---

## 1. 拓扑与权限矩阵

六类 Agent + 一个不是 Agent 的东西（导演）。区分它们的是**权限**，不是提示词。

| 角色 | 读什么 | 写什么 | 能否调别的 Agent | 备注 |
|---|---|---|---|---|
| **角色 Agent** | 自己的卡、场景卡、**自己感知到的**拍、自己的 `cognition` | 无（只产出提案） | 否 | 每角色一个实例 |
| **旁白 Agent** | 场景卡 + 导演下发的**事实白名单** | 无 | 否 | 默认零感知 |
| **规划 Agent** | 全项目设定（只读） | 提案表（大纲/角色/事件卡） | 否 | 用户勾选才落库 |
| **写作 Agent** | 已提交的 beat + 场景摘要 | `revision` | 否 | 不发明事实 |
| **修订 Agent** | 章节 + issue 列表 | 新 `revision` | 否 | 不覆盖旧稿 |
| **审批 Agent** | 全项目 + 检索（只读） | `issue` | **可选**：转修订（独立权限） | 不改稿 |
| **导演（代码）** | 全状态 | `event` + 投影 | 否 | 不是 LLM |

四条硬约束：

1. **模型不持有任何写入权限**。所有输出都是提案，由命令层校验后提交（`01-architecture.md §4`）。
2. **审批 → 修订直连是两个独立开关**：`转发问题` 与 `应用修订`。默认都关。
3. 开启直连后：同 `(chapter, locator, kind)` 的 issue **去重**；总轮次 **≤ 3**；每轮必须给作者一个"接管"出口。否则两个 Agent 会互相"修好"到面目全非。
4. **检索能力只读且限 scope**：审批 Agent 不能读其他项目、不能读 `sensitivity ≥ 3` 的记忆、不能写。

## 2. 六类 Agent 契约

### 2.1 角色 Agent

**输入**：角色卡（稳定）+ 场景卡 + 该角色感知的最近 K 拍 + 该角色已知事实 + 关系快照 + 本拍目标。
**输出**：严格 JSON。

```json
{
  "line":        "台词，可为空字符串",
  "action":      "可被看见的行为/神态",
  "thought":     "心理活动，只有读者可见",
  "intent":      "本拍想达成什么（一句话）",
  "addressed_to":["entity_id"],
  "asserts":     [{"subject":"e_led","predicate":"位于","object":{"id":"e_well"},"claims_true":true}],
  "reveals":     ["fact_id"],
  "emotion":     "calm|tense|afraid|angry|sad|relieved|elated"
}
```

**失败模式与处置**：

| 失败 | 检测 | 处置 |
|---|---|---|
| 输出不是合法 JSON | Zod 校验 | 重试 1 次（附错误位置）；再失败 → 记 `WARN bad_json`，用 `line=""` 兜底并请作者介入 |
| `asserts/reveals` 里有它不知道的事 | 比对 `cognition` | **拒绝该拍**，重试 1 次并附提示"你不知道 X"；再失败 → 记 `knowledge_violation`，展示给作者 |
| 正文里泄露了不知道的事 | 事后抽取器扫描（WARN 级） | 记 `WARN prose_leak`，高亮标出。**不阻断**——抽取器本身有误报（见未验证项） |
| 替别人说话 / 决定别人行动 | 规则 + 抽取器 | 记 `WARN ooc`；连续 3 次 → 该角色本场降权 |
| 复读上一拍 | 与最近 3 拍相似度 > 0.9 | 重试 1 次（提高温度 0.1） |

### 2.2 旁白 Agent

**输入**：场景卡 + **导演下发的事实白名单** + 上一拍摘要。
**输出**：`{"paragraphs": ["...", "..."], "focus": "环境|动作|心理|背景|转场"}`

事实白名单的构造（这是防止旁白变上帝的关键）：

```
narrator_pack =
    location.appearance                       // 地点外观
  ∪ weather/time/scene mood                   // 场面
  ∪ facts(present) where observable = true    // 在场者**看得见**的状态
  ∪ facts where secrecy <= 1                  // 公开信息
  − 任何 secrecy >= 2 且没有在场者知道的
```

导演**不**把秘密给旁白。旁白要写"他攥紧了拳头"，只能来自 `observable` 的行为描述，不能来自"他心里在想什么"。
旁白的 `focus=心理` 只允许写**视角角色**的心理——而视角角色由场景卡指定；写别人的心理直接判 `WARN pov_violation`。

### 2.3 规划 Agent

**输入**：全项目设定（只读）+ 用户需求（自然语言）。
**输出**：结构化提案，`kind ∈ {outline, volume, chapter, scene_block, event_block, character}`。

```json
{
  "kind": "scene_block",
  "title": "雨夜·账本",
  "payload": {
    "goal": {"type":"reveal","subject":"e_led","target":"e_shen"},
    "present": ["e_lin","e_shen"],
    "location": "e_inn",
    "conflict_seed": "沈昼想拿回账本，林砚不肯",
    "exit_conditions": {"op":"any","of":[
      {"op":"fact","subject":"e_led","predicate":"持有","object":{"id":"e_shen"}},
      {"op":"beats","cmp":">=","value":24}]},
    "new_entities": [{"temp_id":"tmp_1","kind":"item","name":"账本","note":"需要作者补全"}]
  },
  "rationale": "为什么这样切"
}
```

规则：
- 引用已有实体必须用 `entity_id`；新实体用 `temp_id` 并标注"待作者确认"。
- **不得直接写 `fact`**。设定提案要经过用户采纳。
- 一次最多生成 3 个场景块，避免"一口气生成整本书"的幻觉雪崩。

### 2.4 写作 Agent

**输入**：已提交的 beat 序列（含旁白）+ 场景摘要 + 上一章结尾 300 字。
**输出**：Markdown 正文（不要求 JSON —— 长文用 JSON 会伤文风）。

规则：
1. **只能重述已提交的事件**。不得新增事实、不得新增角色、不得改变因果。
2. 保留台词的措辞（可微调语气词，不可改语义）。
3. 视点必须与场景卡的 `pov` 一致。
4. 输出长度目标由章纲给出（±20%）。
5. 写完必须返回 `{"facts_used": [...], "beats_covered": [...]}`，供审批 Agent 核对覆盖率。

### 2.5 修订 Agent

**输入**：章节当前 revision + issue 列表 + 作者补充意见。
**输出**：`{"content": "完整新正文", "changes": [{"locator","before","after","why","issue_id"}]}`

规则：
1. **输出完整新 revision**，不是 diff（diff 由系统算）。
2. 每条修改必须挂一个 `issue_id` 或 `author_note`。挂不上的修改 = 擅自改稿，拒绝。
3. 不得删除原文中"已通过审批"的段落，除非 issue 明确要求。
4. 一轮只处理 ≤ 5 个 issue，避免一次改太多无法审查。

### 2.6 审批 Agent

**输入**：章节 revision + 检索结果（事实/认知/关系/前文）。
**输出**：issue 列表。

```json
{
  "issues": [{
    "kind": "knowledge",
    "severity": "blocker",
    "locator": "第 7 段",
    "quote": "「你母亲的忌日快到了。」",
    "why": "沈昼从未被告知林砚母亲的事；cognition 中无对应记录",
    "evidence": {"fact_ids": [], "message_ids": ["m_88"], "expected": "沈昼应不知情"},
    "suggested_fix": "改为林砚主动提及，或删去该句"
  }]
}
```

七类 `kind`：`world`（违背世界观）、`character`（性格/能力越界）、`timeline`（时序矛盾）、`logic`（因果断裂）、`style`（文风）、`pacing`（节奏）、`knowledge`（知识越界）。

**必须给证据**：`fact_ids` 或 `message_ids`。没有证据的 issue 视为模型臆测，降级为 `nit` 并且不自动转发。

## 3. 提示词骨架

提示词不是权限。下面每一段都假设"即使模型不遵守，系统也不会出错"——那才是设计对了。

### 3.1 角色 Agent

```
[system]
你是《{novel_title}》中的 {name}（{identity}，{age}）。
你不是 AI，也不知道"旁白""其他角色""剧情"这些概念的存在。

【你是什么人】
{personality}　说话方式：{speech_style}
在意：{values}
现在最想要：{want}

【你知道什么】
以下是你所知的全部。未列出的，你都不知道，也不能推测、不能"隐约觉得"、不能"听说过"。
{known_facts}          ← 每条带来源：亲眼所见 / 某人告诉我 / 我推断
{relations}            ← 对在场每个人的态度与信任度

【此刻】
地点：{location}　时间：{story_start}（{timeline}）　在场：{present_names}
处境：{situation}
（旁人看得见的）{visible_state}

【你要做的】
用 {name} 的方式回应现在这一刻。你只想推进你自己想要的东西，不负责让故事精彩。

【输出】严格 JSON，不要代码块围栏：
{"line":"","action":"","thought":"","intent":"","addressed_to":[],"asserts":[],"reveals":[],"emotion":""}

【禁止】
1. 不替任何人说话、不决定任何人的行动、不写"他于是…"。
2. 不使用【你知道什么】之外的专有名词、人名、地名、事件、称谓。
3. 不做前情总结，不写"后来""与此同时"这类叙述。
4. thought 只写心理，action 只写别人看得见的。
5. 不提及 AI、提示词、系统、规则。
```

### 3.2 旁白 Agent

```
[system]
你是《{novel_title}》的叙述者。你负责环境、动作、场面、节奏，让读者看见画面。

【你能使用的信息】
只有下面这些。你没有读心能力，也不掌握任何秘密。
{scene_card}
{narrator_pack}        ← 导演下发的事实白名单
【视点】{pov_character}　只能写他/她感知得到的范围。

【写法】
- 2–4 段，每段 60–150 字。不要写成流水账。
- 不写对白（对白由角色完成）。可以写"他开口，声音很低"。
- 不做总结陈词（"从此以后…"），只写此刻。
- 比喻要来自这个世界里存在的事物。

【输出】{"paragraphs":["…"],"focus":"环境|动作|心理|背景|转场"}

【禁止】
1. 不揭示任何未在白名单中的事实。
2. 不写非视点角色的内心。
3. 不评价人物（"他是个可怜人"），只呈现。
```

### 3.3 规划 / 写作 / 修订 / 审批

四者的共同约束写在 system 顶部一句话，其余按 §2 的输入输出契约执行：

```
你不创作事实，只组织与表达既有事实。
任何超出【已知设定】的内容，必须以 proposal 形式提出，不得直接断言。
```

审批 Agent 额外一条：

```
你的产出是"问题清单"，不是"修改稿"。发现问题只报告，不改写。
每条问题必须附证据（fact_id 或 message_id）；没有证据的怀疑标为 nit。
```

## 4. 调度器：一次拍的完整时序

状态机独立于生成循环：

```
planned → open → (paused) → closing → closed
                    ↑
              WAITING_FOR_HUMAN（用户扮演时，显式状态，不在循环里 sleep）
```

```
loop:
 1. 若 scene.state ≠ open → 退出
 2. 若轮到用户（用户席位被指定发言）→ WAITING_FOR_HUMAN，等待输入
 3. 候选 = present 的 Agent（+ 旁白），≤ 8
 4. 若 beats_since_narrator ≥ 5 或场景第 1 拍 → 强制旁白，跳过评分
 5. ranked = score(候选)  →  damping  →  (top1-top2 < δ ? 仲裁 : 直接取 top1)
 6. 为胜者装配上下文（限知，见 §7）
 7. 调用模型 → Zod 校验 → 知识边界校验 →（失败则重试 1 次）
 8. 提交：message + beat + cognition + relation delta
 9. 导演：evalExit → 若满足 → closing；否则
         · 每 6 拍 或 冲突连续 4 拍极差 < 0.05 → 抽事件卡
         · 冲突平坦 → 升 1 级（0 平衡 → 1 摩擦 → 2 对抗 → 3 危机 → 4 决断）
10. 回到 1
```

**用户硬指定**必须同时豁免阻尼与硬上限，并以 `beat.mode='user_pick'` 记录。
否则会出现"用户点了沈昼说话，系统还是让林砚说"——这是最伤信任的一类 bug。

**仲裁只看活着的候选**（`score > 0`）。把被钳制到 0 的候选算进平局判断，会让每一拍都触发仲裁，确定性排序被架空。

## 5. 导演：发牌、升级、叫停

导演是代码。它不是"更聪明的 Agent"，它只做四件机械的事。

### 5.1 事件卡

```
字段：trigger（谓词） + min_level（0–4） + weight + one_shot
抽牌时机：每 6 拍 或 冲突平坦（最近 4 拍极差 < 0.05）
```

三条规则：

1. **触发谓词不满足的牌留在牌堆，不消耗**。否则一场戏抽空牌堆却什么都没发生。
2. `min_level` 防重卡（"有人死了""背叛"）在开场出现。
3. `one_shot` 卡用过即 `consumed`；普通卡回牌堆。

### 5.2 冲突升级阶梯

```
0 平衡 → 1 摩擦 → 2 对抗 → 3 危机 → 4 决断
```

判定平坦：`max(conflict[最近4拍]) - min(...) < 0.05` 且 `turn ≥ 8` → 升一级并抬 `conflict_level`。
没有阶梯，冲突会在 0.2 附近来回抖动，戏永远起不来。

### 5.3 收束

每拍评估 `exit_conditions`（见 `01-architecture.md A5`）。满足 → `closing`，再写 1 拍收束旁白 → `closed`。
到 `max_beats` 未满足 → 关闭 + `WARN exit_conditions_unsatisfied` + 未结线索清单。**不静默截断**。

### 5.4 记事件

每次状态变更写 `event`。事件不是读路径（读的是投影表），它的用途是：审计"这一拍改了什么"、支撑回退重放、出 bug 时重建投影。

## 6. 三层记忆的落地

**三层不是三个库，是三种 scope + 三种预算**。同一张 `memory_node` 表，靠 `kind` 与 `owner_id` 区分。

| 层 | 内容 | 注入方式 | 预算 |
|---|---|---|---|
| **长期** | 世界观、角色卡、主线、已发生事件 | `pinned` 单独成段 + 检索 top-k | 25% |
| **场景** | 本场摘要、当前目标、关系变化 | **常驻**（不检索，直接注入） | 15% |
| **短期** | 该角色感知的最近 K 拍原文 | 按受众过滤后取最近，封顶 16 拍 | 30% |

**写回时机**（避免每拍写放大）：

| 时机 | 写什么 |
|---|---|
| 每拍 | `message` / `beat` / `cognition` / `relation` |
| 场景关闭 | 场景摘要节点 + `DERIVED_FROM` 边（指向被压缩的拍） |
| 冲突升级 / 事件卡生效 | `event` 节点，`importance` 按“是否改变目标”加权 |
| 手动 | 作者标记"记住这个" |

**摘要可回溯**：`DERIVED_FROM` 指向 children，原文永不因压缩删除，只降权。触发器 `ck_memory_has_children` 禁止物理删除有子节点的记忆。

**一个反直觉的结论**：小说项目里"遗忘"不是目标。设定（`fact`）永不衰减，`relationship` 永不衰减，`clue` 也不衰减——它靠 `resolved_seq` 退出召回，不靠时间（给伏笔设半衰期，等于保证它在回收前先被忘掉）。只有 `event`（30 天）和 `summary`（180 天）会衰减。理由见 `01-architecture.md A4`。

## 7. 每个 Agent 拿到的上下文（这是需求 6 的正面回答）

同一场戏里，五个 Agent 的上下文**完全不同**。差异不是"提示词里说你不知道"，而是**内容根本不出现**。

| 段 | 角色 | 旁白 | 规划 | 写作 | 修订 | 审批 |
|---|---|---|---|---|---|---|
| 角色卡 | 只自己 | 无 | 全角色（摘要） | 出场角色 | 出场角色 | 全角色 |
| 场景卡 | ✓ | ✓ | 章纲层 | ✓ | ✓ | ✓ |
| 最近拍 | **仅自己感知的** | 仅上一拍摘要 | 无 | 全部已提交 | 全部 | 全部 |
| 已知事实 | **仅自己 cognition** | 白名单 | 全部（只读） | 引用清单 | 引用清单 | 全部 + 检索 |
| 关系 | 对在场者 | 无 | 关系网 | 无 | 无 | 关系网 |
| 秘密 | 仅自己知道的 | **不下发** | 全部 | 无（不写秘密解释） | 无 | 全部 |
| 其他角色内心 | **永不下发** | 仅视点角色 | 无 | 无 | 无 | 无 |

具体到"某个角色不在场时发生的事"：

1. 那场戏的消息 `audience` 不包含它 → 不产生 `cognition` 行。
2. 后续任何装配中，`visibleFacts` 过滤掉它。
3. 除非：有人在本场**告诉**它（新消息的 `audience` 含它，且 `asserts` 匹配该事实）→ 新增 `cognition(percept='told')`。
4. 或者：旁白以**公开场面**的方式呈现（导演把它加入 `narrator_pack` 且 `secrecy ≤ 1`）→ 它作为"在场目击者"获得 `witness`。

**没写第 5 条。** 没有"它应该能猜到"这种路径。

## 8. 冲突检测

五类，前两类阻断，后三类告警。

| # | 类型 | 检测点 | 判定 | 处置 |
|---|---|---|---|---|
| 1 | **知识越界** | 提交前 | `asserts/reveals` 中的 fact 不在 actor 的 `cognition` | 阻断 + 重试 1 次 + 记 `knowledge_violation` |
| 2 | **设定冲突** | 提交前 | claim 与 `locked` 事实矛盾（同 slot_key，不同 object） | 阻断 + 记 `setting_conflict` |
| 3 | **关系突变** | 提交前 | 单拍 `|Δ| > 0.35` | 要求理由；无理由则钳制到 ±0.35 并记 `relation_jump` |
| 4 | **时间线矛盾** | 提交前 | 同一 `timeline` 内 `story_start` 倒退（闪回必须显式换 timeline）；物品同时被两人持有（单值槽位自动拦） | 阻断 |
| 5 | **视角/称谓** | 提交后 | 使用了仅他人知道的称呼；非视点角色出现内心描写 | `WARN` + 高亮 |

第 1 类的第二道防线（正文抽取）只告警不阻断，因为抽取器会误报。**两个口径在报告里必须分开写**：
- 结构化断言越权率（可精确判定，门禁卡这个）
- 正文抽取越权率（含模型行为与抽取误差，只作观察）

把它们合成一个数字，就无法区分"过滤失败"和"生成失败"。

### 8.1 「重写这一拍」的三种语义

按钮只有一个，但语义不能靠猜。点下去先让用户选，默认第一个：

| 选项 | 做什么 | 对后续的影响 | 数据表现 |
|---|---|---|---|
| **重写（开分支）** | 从该拍新建分支，重跑一次 | 旧分支的后续完整保留、随时可读 | `branch(parent, fork_seq=该拍序号)` |
| **仅替换** | 新消息 `supersedes_id` 指向旧消息 | 后续 beat 标 `stale=1`，顶部横幅提示"后续 5 拍基于旧文本" | `message.supersedes_id` + `beat.stale` |
| **重写并重跑** | 替换 + 自动重新生成后续 N 拍 | 后续被覆盖（仍可回退到检查点） | 上述两者 + N 条新 beat |

默认必须是**开分支**。原地替换会让后面五拍在回应一句已经不存在的话，而界面上没有任何提示——这是最难排查的一类错误：读起来只是"人物忽然答非所问"。

`supersedes_id` 上有部分唯一索引：**一条旧消息只能被替换一次**。否则追溯链会分叉，UI 无法判断哪个才是现行版本。

## 9. 一次真实的拍：端到端

```
[场景] s17 雨夜·账本  状态 open  冲突 2.1  已 11 拍
[候选] 林砚(goal 1.0, stake .47, addressed 0) / 沈昼(1.0, .57, 1) / 祁昭(0, .27, 0)
[评分] 沈昼 .340+.300+.090+.000+.048 = .778（+抖动 .021 → .799）；林砚 .340+0+.074+0+.072 = .486
[仲裁] top1-top2 = .313 > δ(.05) → 不仲裁，直接取沈昼
[上下文] 沈昼 6.1k → 装配 4.3k：卡 600 / 场景 400 / 最近 9 拍 1.3k
         / 已知事实 34 条 900 / 关系 3 人 380 / 线索 200 / 契约 520
[模型] JSON 合法 → asserts 命中 cognition 3/3 → 通过
[提交] event 4127；message m_913（audience=[e_lin, e_qi]）；
       cognition 新增 2 行（林砚、祁昭 听见了）；
```

每一步都可在 UI 里展开：`beat.breakdown` 给出五项分值，`message.audience` 给出谁听见了，`cognition` 给出谁知道。
**"这一拍为什么是它说话"必须能回答**，否则调度器就是一个黑箱，调参全靠感觉。

## 10. 存量稿导入

真实用户手上都有一部写了一半的书。没有导入管线，产品只对"从零开始"的人可用——而这批人恰恰最少。

四步，每步可中断续跑：

```
① 切分   Markdown → 章 → 场景候选（按空行、时间/地点变化切，允许手工调整边界）
② 抽取   实体（人名/地名/物名）· 事实（谁在哪、谁持有、谁知道）· 关系（称谓与态度）
③ 确认   批量确认 UI：一次过 50 条，左"原文引用"右"抽取值"，可改可弃
④ 回填   先按"作者全知"建 fact（truth=1），再按场景出场与对话建 cognition
```

三条硬规则：

1. **抽取结果只进 proposal，不进 `fact`**。作者确认才算数。一次错误抽取写进事实库，后面四十章都会被它污染，而且越晚发现越贵。
2. **回填 `cognition` 按出场顺序，不按"作者知道"**。否则所有角色一开局就全知，限知直接失效——这是导入功能最常见的自毁方式。
3. **导入必须幂等**。同一份稿重复导入不产生重复实体，靠 `entity(branch, kind, name)` 唯一索引兜底；失败半步重跑不会留下半本书。

导入完成后的第一件事不是生成，而是跑一次**冲突扫描**：物品持有是否唯一、时间线是否单调、同一角色是否有两条矛盾的认知。三份清单直接给作者勾选修正。

## 11. 质量仪器：两条不写进架构就会烂掉的指标

这两条不影响"能不能跑通"，但决定"好不好用"。没有仪器，退化是静默的。

### 11.1 声音区分度

多角色 AI 小说最常见的失败不是逻辑错，是**所有人说话像同一个人**。

```
voice_distance(a, b) = 0.6·√JSD(句长分布) + 0.4·mean(|Δ口头禅密度|, |Δ第一人称率|, |Δ问句率|)
```

- 句长分 4 档（≤8 / 9–16 / 17–28 / ≥29 字），取每人最近 20 句的分布。
- 阈值 `0.18`。低于阈值 → 场景关账时提示「沈昼与林砚的声音过于接近（0.11）」。
- 运行时机：每场 `closed` 后，对在场角色两两计算。纯统计，无模型调用，成本可忽略。
- **已知局限**：只抓"结构性相似"（句长、口头禅、语气），抓不到"都用同一种比喻"这类语义同质化。后者只能靠人工盲测——去掉名字让作者猜这句是谁说的。

探针里有 `voice_distance()` 与四条断言：同样本距离 = 0、两种笔调 > 阈值、空样本返回 0 不抛错、结果有界。

### 11.2 伏笔回收率

`memory_node(kind='clue')` 配 `resolved_seq`，视图 `v_open_clue` 就是"埋了没收"的清单。

- 每卷关账输出：未回收线索 N 条，逐条给「埋设章 / 距今章数」。
- 超过 `clue_max_age_chapters`（默认 15 章）标红。
- 审批 Agent 把"读者早忘了的伏笔"报成 `pacing` 类 issue，而不是 `logic`——它不是错，是节奏问题。

这两条不放进 P0/P1 门禁（它们衡量"好看"，不是"正确"），但必须在 P3 之前接上，否则第一部长篇就会栽在这里。

## 12. 文本生成服务的四条线

需求里的"对话 / 旁白 / 章节润色"不是三个 Agent，是**产物不同的四条生成线**。混在一起就会出现"润色时顺手把剧情改了"。

| 线 | 输入 | 产物 | 谁负责 | 能否改事实 |
|---|---|---|---|---|
| **对话** | 限知上下文 | 一条 `message`（台词/动作/心理/意图） | 角色 Agent | 否，只能 `asserts`，不能写 `fact` |
| **旁白** | 场景卡 + 事实白名单 | 一组段落（`message`，audience 为空） | 旁白 Agent | 否 |
| **成稿** | 已提交的 beat 序列 | 一个 `revision`（整章） | 写作 Agent | 否，只重述 |
| **润色** | 现有 revision + 目标 | 一个新 `revision` | 修订 Agent | 否 |

### 12.1 润色的三种触发

润色与"按 issue 修订"是两个入口，最容易糊在一起：

| 触发 | 输入 | 挂什么 | 典型用法 |
|---|---|---|---|
| **按 issue 修订** | issue 列表 | 每条修改必须挂 `issue_id` | 审批后的问题 |
| **整体润色** | 章节 + 目标（"更克制""去掉形容词堆砌"） | 挂 `author_note` | 作者对文风不满意 |
| **局部润色** | 选中段落 + 目标 | `author_note` + 段落定位 | 只想改一段 |

规则：`revision.changes[]` 每条修改**必须**至少有一个 `issue_id` 或 `author_note`。都没有 = 擅自改稿，提交层直接拒绝。这条同时覆盖了修订与润色两个入口。

### 12.2 润色的硬约束

1. **不改事实**。润色前后的 `asserts` 集合必须一致（抽取器比对）。把"他握紧了刀"润成"他拔出了刀"是改事实，不是润色——后面所有依赖这个动作的拍都会错。
2. **不改对话语义**。台词可调语序、语气词，不可改意思。判定：去掉标点与语气词后，句向量相似度 ≥ 0.85。
3. **不增删段落**，除非 `author_note` 明确要求。
4. **必须产出完整新 revision**（不是 diff），diff 由系统算——这样每次润色都可回退、可对比、可逐条接受或拒绝。

### 12.3 润色的验收

| 指标 | 阈值 | 怎么测 |
|---|---|---|
| 事实漂移 | **0 处** | `asserts` 集合差集 |
| 语义漂移 | 台词相似度 ≥ 0.85 | 去停用词后比对 |
| 字数变化 | ±15% | 除非 `author_note` 指定 |
| 修改可追溯 | 100% 挂 `issue_id` 或 `author_note` | 校验 `revision.changes` |

第 1 条是硬门。事实漂移不会报错，只会让作者觉得"人物怎么突然变了"——而那时已经改了二十章。
