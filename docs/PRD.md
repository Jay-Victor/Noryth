# Noryth 产品设计文档

> 版本 v0.6 ｜ 状态：设计草案 ｜ 技术基线：Electron 桌面端（Windows 首发）｜ 范围：M0–M2
>
> 本版已收口：6 个 Agent 的职责边界 · 默认逐拍 + 自动模式显式开启 · 审批与定稿分离 · 角色私有记忆隔离 · 正文/轨迹/依据三分 · 工具与 Agent 解耦（单一注册表 + 角色白名单 + 运行时注入身份）
>
> v0.6 设计决策：工具层单一注册表 · 42 个 Agent 可调用工具 + 8 个系统能力 · 提案与提交分离 · `grounding` 收紧为工具返回引用的子集
>
> 既有产品决策（v0.4）：个人作者 · Windows 10/11 · 云端 API（OpenAI / DeepSeek / 通义）· 设置中逐 Agent 选模型 · 不支持导入 · 默认逐拍 · NSIS + GitHub Releases 自动更新

**阅读指引**：如果只看四节，看 §0.5（三个最贵的错误）、§4.3（权限矩阵）、§4.9（工具层）、§6.2（演绎流程）。这四节决定了产品能不能成立，其余是落地细节。

## 0. 摘要

### 0.1 一句话

Noryth 是一个桌面端的多 Agent 小说创作工作台：作者定蓝图与分镜，角色与旁白按拍演出，审批与记忆固化把「这一章」变成「下一章的资产」。

### 0.2 真正的问题

通用写作工具优化的是「下一段写得好不好」；长篇的真正失败点是**写长了就崩**：

- **人物声音漂移**：第 30 章的主角像换了一个人。
- **设定自相矛盾**：第 12 章说左手受伤，第 20 章双手抱拳。
- **限知被打破**：角色说出了它不该知道的事，谜底提前泄漏。
- **伏笔失收**：埋了 40 章的线，没人记得。
- **改一章崩一片**：改一句台词，世界状态、角色记忆、后续章节全部不同步。

Noryth 不解决「文笔灵感」，它解决**长篇的一致性、可追溯性与可回退性**。

### 0.3 四个设计支点

1. **蓝图先行，分镜驱动**：不是让 Agent 自由聊天，而是先有可审阅的分镜，再按拍生成。自由对话适合演示，不适合长篇。
2. **限知即权限**：角色的知识边界在上下文装配层强制，不写在提示词里靠模型自觉。
3. **正文 / 轨迹 / 依据三分**：只有正文进入下一轮与稿件；思考轨迹只进 UI 与归档。
4. **单一写入者 + 人类闸门**：每个文件只有一个 Agent 有写权；「审批通过」与「作者定稿」是两个动作。

### 0.4 核心闭环

```
规划 → G1 蓝图 → 角色注册/建库/世界初始化 → G2 分镜
     → 演绎（G3 逐拍确认 / 自动模式）→ 初稿
     → G4 审批 → G5 修订 → G6 定稿 → G7 记忆固化 → 下一章
```

### 0.5 三个最贵的错误（本设计要避免的）

| 错误 | 失效机制 | 代价 |
|---|---|---|
| 让审批同时「裁判 + 定稿」 | 生成者与评判者同源，评分通胀；没有人类动作，质量闸门形同虚设 | 整章返工，且无法追责 |
| 角色记忆共用一个库，靠提示词禁止越界 | 一次相似度召回就把别人的秘密送进上下文；事后无法检测 | 泄底影响整卷，读感不可逆 |
| 单一可变世界状态 + 单时间轴 | 闪回被判成矛盾；回退后状态对不上；审批用「当前认知」审早期章节 | 数据模型返工，已写章节全部重审 |

### 0.6 与原始设想的七处修正

| 原始设想 | 问题 | 本设计的处理 | 落点 |
|---|---|---|---|
| 「审批通过或用户确认通过、定稿」 | 审批 Agent 同时拥有裁判权与定稿权，质量闸门失效 | `approved` 与 `finalized` 拆成两个状态；G6 只能由作者触发 | §2.3、§5.3 |
| 审批「负责质量把关」又要「修改章节初稿」 | 裁判兼改稿人，修订没有边界与次数上限 | 报告 / 修订 / 定稿三权限分离；修订走结构化 patch，只写草稿区，逐条复检，最多 3 轮 | §4.3、§5.3 |
| 世界状态是「当前时间、地点、全局事件、角色状态」 | 单一可变快照回答不了「第 3 章时角色知道什么」，回退也无法恢复 | append-only 事件/事实 + 按章投影 + as-of 查询 | §7、§8 |
| 角色记忆「追加到向量知识库」 | 直接追加会把错误、过期、被改稿的内容永久固化；台词被当成事实 | 提案制 + `source_revision` + 信念/事实分离 + 可重建 | §6.4、§7.2 |
| 旁白「可读取小说纲要」 | 纲要含未揭示的谜底，旁白可能提前泄漏 | 旁白读结构，但事实受 `reveal_seq` 约束 | §8.2 |
| 自动模式「按顺序输出」 | 没有停条件，分镜耗尽后会即兴续写或死循环 | 机器可判定的收束条件 + 拍数/预算上限 + 分镜耗尽告警，不即兴补写 | §6.2、§6.6 |
| 输出三部分都进入文档/上下文 | 轨迹含私有记忆 ID 与推理，跨角色传递等于泄密，且 token 成本远高于正文 | 只有 `body` 进下一轮；`trace` / `grounding` 只进 UI 与归档 | §4.6、§8.1 |

## 1. 产品定位

### 1.1 目标与非目标

| 维度 | 目标 | 非目标 |
|---|---|---|
| 用户 | 写 10 万字以上长篇的个人作者；首发只服务单人 | 短篇文案、一次性营销稿、完全零设定的「一句话生成小说」；小型工作室与多人协作（M0–M2 不做） |
| 场景 | 有想法，愿意在应用内从零建立蓝图；执行不稳定，需要一致性与可回退 | 导入现有小说/大纲；多人实时协作、云端协同编辑（M0–M2 不做） |
| 平台 | Windows 10/11 x64 首发 | macOS / Linux 正式支持（架构保持可移植，M0–M2 不做） |
| 产出 | 可导出的 Markdown / TXT / DOCX 章节稿 | 自动发布、签约投稿、版权交易 |
| 使用前提 | 作者愿意投入蓝图/角色卡/分镜；有 OpenAI / DeepSeek / 通义任一 API Key | 作者完全不想做设定，且没有任何模型接入条件 |

### 1.2 产品形态

- **Electron 桌面端，Windows 10/11 x64 首发，项目本地存储**：项目是一个文件夹，SQLite 是状态权威，Markdown 是受控镜像。
- **模型接入**：云端 API Key 调用；内置 OpenAI / DeepSeek / 通义预设；设置中逐 Agent 绑定 provider + model；统一走 OpenAI-compatible 适配器。
- **需要联网生成**：无网络时仍能编辑、审阅、查看记忆与导出；生成与审批需要云端调用。
- **Windows 分发**：NSIS 安装包 + 自动更新（GitHub Releases）。
- **单机单用户**：项目锁防止同一项目被两个窗口同时写；不做账号体系、不做多人协作。
- **可导出**：Markdown、TXT、DOCX；导出是快照，不是新的真相来源。

### 1.3 差异化

通用写作 AI 的卖点是「生成快」；Noryth 的卖点是「第 30 章仍然像同一个人写的」。

具体差异不在模型，而在三件事：

1. **角色有私有记忆，且记忆有边界**：不是把整本设定塞进提示词。
2. **分镜是合约**：每一拍谁说话、要完成什么、什么时候停，都是可审阅的结构，不是模型即兴。
3. **改稿有代价可计算**：改一拍会标脏下游，改一章会重建记忆，回退能恢复全部状态域。

### 1.4 五条铁律

| 编号 | 铁律 | 含义 |
|---|---|---|
| R1 | 作者定稿权不可代理 | 审批通过不等于定稿；定稿只能由作者点击 |
| R2 | 一个文件只有一个写入者 | 正文、纲要、角色卡、记忆、世界状态各有唯一写入口 |
| R3 | 限知由权限强制 | 角色只能检索到「它有权知道」的内容，隔离在接口层，不在提示词里 |
| R4 | 正文与轨迹分离 | `body` 进稿件与下一轮；`trace` / `grounding` 只进 UI 与归档 |
| R5 | 一切状态可回退 | 正文、记忆、世界状态、关系图都能回到某个检查点，且能重建 |

## 2. 核心概念

### 2.1 术语表

| 术语 | 定义 |
|---|---|
| 蓝图 | 规划阶段的产物：题材、大纲、主线、卷纲、章纲、角色卡、世界初值 |
| 分镜 | 一章的场景与拍列表：谁在什么场景、第几拍、说什么、要完成什么、何时收束 |
| 拍（beat，又称轮次） | 一次 Agent 输出：一个角色的一段台词/心理/动作，或旁白的一段叙述 |
| 逐拍模式 | 默认模式：每拍输出后等作者确认/重生成/编辑，确认后才进入下一拍 |
| 自动模式 | 作者显式开启的加速档：按分镜连续生成，只在收束、预算、冲突时暂停 |
| 角色卡 | 角色的系统提示词与设定：身份、性格、说话方式、欲望、禁忌、已知关系 |
| 私有记忆 | 某个角色独有的经历、认知、关系变化；存放在该角色的私有向量知识库中，其他角色不可检索 |
| 公共设定 | 世界观常识、地理、历史、组织等可公开检索的资料 |
| 世界状态 | 客观事实、事件、角色状态、关系边的当前投影（即原始设想中的「世界状态机」），不是一份可变大 JSON |
| 关系图 | 角色之间的关系边与张力变化（即「角色关系图谱」）；有时间轴，可回放 |
| 初稿 | 一章的草稿区正文；可被重新生成、编辑、patch |
| 定稿 | 作者确认后的章节快照；不可被审批或记忆管理修改 |
| 记忆固化 | 定稿后抽取增量，写入角色记忆、世界状态、关系图的过程 |
| 闸门（Gate） | 需要作者显式决策的节点；不通过就不能进入下一步 |
| 调度器 | 代码组件，负责按分镜发牌、暂停、收束、记事件；不生成正文 |
| 文档写入控制器 | 代码组件，所有正文落盘的唯一入口；负责 revision、hash、冲突检测 |
| 工具（tool） | Agent 唯一的能力出口：带清单、版本、副作用声明与作用域的受限函数；未注册不可调用，未授权不出现在模型工具列表 |
| 工具注册表 | 全部工具清单与实现的唯一目录；决定工具定义、版本与可见性 |
| 工具集（toolset） | 某个 Agent 实例在某个任务开始时解析并快照的有效工具白名单；中途不随设置变化 |
| 提案型工具 | 只产出结构化提案、不落盘的写类工具；落盘由文档控制器或 G7 后的应用器执行 |

### 2.2 叙事层级

```
作品（project）
└─ 卷（volume，属于 outline_node）
   └─ 章（chapter）
      └─ 场景（scene）—— 一章 2–5 个场景，章与场景是多对多
         └─ 拍（beat）—— 一次角色或旁白输出
```

两个容易晚发现、发现就要改表的结构：

- **章与场景是多对多**：用 `chapter_scene(chapter_id, scene_id, ord)` 连接，`UNIQUE(chapter_id, ord)`。只靠 `chapter_id` 外键，写起来就不知道「这一章该演哪几拍」。
- **时间要拆三条轴**：`story_start` / `story_end`（故事内时间）、`idx`（叙事顺序）、`timeline`（main / flashback / dream）。合成一个 `story_time`，闪回会被判成时间线矛盾。

### 2.3 闸门表

| 编号 | 时机 | 作者决策 | 通过后系统动作 | 拒绝/退回 |
|---|---|---|---|---|
| G0 | 新建项目 | 题材、目标篇幅、视角、内容边界 | 创建项目与空蓝图 | 返回项目列表 |
| G1 | 规划完成 | 蓝图、主线、卷纲、章纲、角色卡是否可执行 | 注册角色、创建私有记忆库、写公共设定、初始化世界状态 | 回到规划对话，保留草案 |
| G2 | 每章开演前 | 分镜是否按这个顺序演 | 开场景，进入演绎 | 改编排对话或直接改分镜 |
| G3 | 逐拍模式（默认）下每一拍 | 这一拍是否接受 | 确认并提交；进入下一拍 | 重新生成；不进入下一拍 |
| G4 | 初稿完成 | 是否接受审批报告、是否授权修订 | 生成 patch 提案，进入修订 | 退回创作台继续改 |
| G5 | 修订执行前 | 哪些 patch 接受、哪些拒绝 | 文档控制器落盘，生成新 revision | 保留原 revision，审批重新出方案 |
| G6 | 修订完成 | 是否定稿 | 冻结章节快照，触发记忆固化 | 继续修订或回退 |
| G7 | 记忆固化前 | 增量条目、世界状态、关系变化是否入库 | 写向量库、世界状态、关系图 | 逐条编辑/拒绝，不写库 |

> G3 不是一次性闸门，而是「每拍一次」的微闸门。默认逐拍模式下 G3 是主路径；自动模式是作者显式开启的加速档，跳过 G3，但 G4/G6/G7 仍然必须经过作者。

## 3. 用户场景

### 3.1 从零到第一章定稿

| 阶段 | 作者动作 | 系统动作 | 产物 |
|---|---|---|---|
| 立项 | 输入一句想法：「民国背景，一个替人写遗书的女子，发现父亲留下的账本」 | 规划 Agent 追问题材、视角、篇幅、禁忌；给出 2–3 个方向 | 项目 + 对话记录 |
| 规划 | 在多轮对话中改主线、加角色、删设定 | 生成大纲、主线、卷纲、章纲、角色卡草案；做覆盖检查 | 蓝图草案 |
| G1 | 审蓝图，改两个角色的动机，确认 | 注册 5 个角色；建 5 个私有记忆库 + 1 个公共设定库；写世界初值 | 可创作的项目 |
| 分镜 | 看编排给出的 3 场 24 拍，删掉一场，调整两拍顺序 | 编排重新校验发言人在场、意图与出口条件 | 分镜 v2 |
| 演绎 | 默认逐拍：前 6 拍确认 4 拍、重生成 2 拍；之后作者显式切自动模式跑完 | 角色/旁白按拍输出；文档控制器写入草稿；调度器检查收束 | 初稿 |
| 审批 | 看报告：1 个知识越界、1 个章纲冲突、5 条建议；追问两条 | 审批解释证据；不自动改稿 | 审批报告 |
| 修订 | 授权 2 条 patch，逐条接受 | 只改草稿；生成新 revision；复检受影响维度 | revision v2 |
| 定稿 | 点「定稿」 | 冻结快照；触发记忆固化提案 | 定稿章节 |
| 固化 | 审 14 条增量，删 2 条，改 1 条，确认 | 写向量库、更新世界状态与关系图 | 下一章可用的记忆 |

### 3.2 作者净操作时间

M0 就要开始埋点，但不在本文拍一个目标数字。需要区分：

- **阅读时间**：作者看正文、看报告，这是产品价值，不是成本。
- **净操作时间**：点击、输入、切页、等待确认的耗时。
- **返工时间**：因为状态不同步、记忆错误、越界泄漏导致的重复劳动。

M1 用真实项目日志建立基线，再定「每千字净操作时间」的目标；没有基线就定目标，只会得到一个拍脑袋的数字。

默认逐拍意味着「确认」是最高频操作。M0 要把确认/重生成/编辑做成键盘可达的一键动作，并单独测「每拍确认耗时」；否则逐拍会把阅读时间变成操作负担。

## 4. 系统架构

### 4.1 分层

| 层 | 组件 | 职责 | 不做什么 |
|---|---|---|---|
| 界面层 | Electron renderer（React + TypeScript） | 项目库（首页）、规划台、创作台、审批台、记忆台、设置；流式展示；diff 审阅 | 不直接读写文件、不持有 API Key |
| 编排层 | 调度器、闸门管理器、文档写入控制器（main process） | 按分镜发牌、暂停/恢复、收束判定、落盘、版本与 hash | 不生成正文、不替作者做质量判断 |
| Agent 层 | 6 个 Agent | 规划、编排、角色、旁白、审批、记忆管理 | 不越权写、不跨角色检索 |
| 工具层 | 工具注册表 + 42 个受限工具（结构、检索、校验、提案、执行）+ 8 个系统能力 | 给 Agent 提供受限、可审计、可替换的能力出口；身份与作用域由运行时注入 | 不把数据库内核对象、SQL、文件路径交给模型；不拼上下文、不做业务裁决（§4.9） |
| 存储层 | SQLite（状态权威）+ 向量索引 + Markdown 镜像 | 持久化、事务、备份、恢复 | 不让 Markdown 成为第二真相 |
| 模型层 | 云端 API 适配器 + 模型路由 | 内置 OpenAI / DeepSeek / 通义预设；按 Agent/任务选模型；能力探测、重试、降级、计量 | 不把供应商差异泄漏到业务逻辑 |

界面采用**四分区工作台** + 左侧 56 px 导航：会话列表、对话聊天、文件预览、文件树。四分区是信息架构，不等于四栅永远并列：≥1600 px 四栅并列（默认 248 / 485 / 583 / 224）；1360–1599 px 文件树收为 44 px 轨道 + 320 px 临时抽屉；1280–1359 px 会话列表再收为 64 px 轨道。折叠后正文列保持 486–543 px（32–36 字/行），这是「四分区」与「可读正文」的唯一交集：1440 px 强行四栅只剩 431.8 px、28.8 字/行，低于 32 字下限。六页布局、状态与键盘路径见 `docs/UI-DESIGN.md`，栅格数字由 `docs/scripts/check_ui_spec.py` 断言。

### 4.2 Agent 编制与边界

| Agent | 核心职责 | 可写范围 | 隔离级别 | 失败退化 |
|---|---|---|---|---|
| 规划 | 把想法变成蓝图；多轮对话定题材、大纲、主线、卷纲、章纲、角色卡 | 蓝图草案、角色卡草案、注册清单（提交） | 不接触正文与记忆 | 对话超轮次 → 输出当前草案 + 未决项清单 |
| 编排 | 读纲要与状态，拆分镜；与作者讨论场次；把分镜交给调度器执行 | 分镜、每拍指令（提交） | 不读角色私有记忆；不生成正文 | 分镜冲突 → 标 `storyboard_conflict`，暂停等作者 |
| 角色 | 扮演单个角色，生成台词、心理、动作 | 自己的 `body`（提交） | 仅自己的卡 + 自己的记忆 + 限知世界状态 | 检索为空 → 只用卡与场景，标 `memory_empty` |
| 旁白 | 环境、动作推进、心理旁白、转场、时间推进 | 自己的 `body`（提交） | 公开设定 + 读者已知投影 + 本章结构；不读私有记忆 | 事实不足 → 只写可感知画面，不补设定 |
| 审批 | 审初稿；出报告；作者授权后改草稿 | 报告、patch 提案（提交） | 初稿/设定/记忆只读；修订走 patch；不改定稿 | 报告 schema 失败 → 降级纯文本报告，阻断项仍需定位 |
| 记忆管理 | 建库；定稿后抽取增量；更新世界状态/关系图 | 记忆条目、世界状态、关系图（提案后执行） | 只读定稿；不改正文 | 抽取失败 → 保留原状态，job 标 `failed` 可重试 |

### 4.3 权限矩阵

图例：**读** = 只读；**写** = 可直接修改；**提交** = 只能产出结构化内容，由文档控制器落盘；**建议** = 产出提案，需他人确认；**建库** = 创建命名空间与初始条目；**—** = 不可访问。

| Agent | 蓝图 | 角色卡 | 分镜 | 初稿 | 定稿 | 私有记忆 | 公共设定 | 世界状态 | 审批报告 | 记忆写入 |
|---|---|---|---|---|---|---|---|---|---|---|
| 规划 | 提交 | 提交 | — | — | — | — | 读/建议 | 建议 | — | — |
| 编排 | 读 | 读 | 写 | 提交 | 读 | — | 读 | 读 | 读（摘要） | — |
| 角色 | 读（脱敏目标） | 读（自己） | 读（本拍） | 提交 | — | 读（自己） | 读（公开） | 读（限知） | — | — |
| 旁白 | 读（本章结构/脱敏目标） | 读（公开投影） | 读（本拍） | 提交 | — | — | 读 | 读（读者投影） | — | — |
| 审批 | 读 | 读 | 读 | 读/建议（patch） | 读 | 读（审计） | 读 | 读 | 写 | — |
| 记忆管理 | 读 | 读 | — | — | 读 | 建库/写 | 建库/写 | 写 | 读 | 写 |
| 文档控制器 | — | — | — | 写 | 写（落盘） | — | — | — | — | — |
| 作者 | 写/批准 | 写/批准 | 改 | 改/确认 | 定稿 | 查看/失效 | 写 | 写/批准 | 读 | 确认/编辑 |

> 矩阵中的「文档控制器」与「调度器」不是 Agent，是代码组件；列在这里是为了把写入边界画全。真正的 Agent 只有 6 个。

四项检查：

- 每个「写」都有对应闸门与授权人：分镜由 G2 管，初稿由 G3/G4 管，定稿由 G6 管，记忆由 G7 管。
- 没有人同时握有「生成 + 定稿」或「审批 + 定稿」：审批有 patch 权，没有 G6 权。
- 隔离在工具层强制：检索接口的 `character_id` 由调用方身份注入，不接受模型传参；越权查询返回空并记审计，不返回「无权限」提示（避免模型试探）。
- 每个「读」「提交」「建议」都对应具体工具（§4.10），且工具白名单由角色基线 ∩ 实例收窄 ∩ 项目策略解析（§4.9.3）；矩阵与工具清单冲突时以矩阵为准，并视为工具粒度设计缺陷。

### 4.4 三条硬红线

1. **角色 Agent 永远不写记忆、纲要、别人的正文**；它的输出只归属于当前 `speaker_id`，不能替其他角色说话。
2. **编排 Agent 永远不生成正文；旁白永远不裁决事实**。谁说话、何时停、发生什么事件，是调度器与分镜的职责；旁白只写可感知的叙述。
3. **审批 Agent 永远只在草稿区改 patch；记忆管理 Agent 永远不改正文**。审批不改定稿、设定、记忆、世界状态；定稿只能由作者触发。

### 4.5 单拍数据流

1. 调度器从分镜取下一拍。分镜必须指定 `speaker`；Noryth 不做无分镜的角色自由演绎，因此不引入发言评分器与仲裁阈值。
2. 上下文装配器按 L0–L3 组装（见 §8.1）；`actor_id` 由调用方注入，检索前先做可见性过滤。
3. 工具层按该 Agent 的 `toolset` 快照执行调用：角色私有记忆 / 公共设定 / 结构化世界状态；`actor_id`、`character_id`、`as_of` 由运行时注入，返回带 ID 的引用（§4.9.4）。
4. Agent 生成统一信封：`trace` / `body` / `grounding` / `meta`。
5. 校验器检查 schema、`speaker_id` 归属、`grounding` 引用是否在允许集合内、字数与格式。
6. 文档控制器把 `body` 写成当前 revision 的新 beat（草稿区），不碰定稿。
7. UI 展示：正文、折叠的轨迹、依据 chips、上下文检查器入口。
8. 逐拍模式（默认）→ 进入 `WAITING_FOR_HUMAN`；自动模式（显式开启）→ 进入下一拍。
9. 逐拍模式下：作者确认 / 重新生成 / 直接编辑；重新生成写 `supersedes_id`，不物理删除。
10. 场景收束 → 章草稿完成 → G4 审批；审批通过后作者 G6 定稿 → G7 记忆固化。

### 4.6 Agent 输出信封

```json
{
  "turn_id": "bt_045",
  "speaker": {"type": "character", "id": "char_lin"},
  "trace": [
    {"type": "thought", "text": "她不能直接问账本，先试探他对父亲的态度。"},
    {"type": "tool_call", "call_id": "tc_01", "tool": "memory.retrieve_own", "args": {"query": "父亲 账本"}, "runtime_args": {"character_id": "char_lin", "as_of": 312}, "result_ids": ["mem_101", "mem_108"]},
    {"type": "tool_call", "call_id": "tc_02", "tool": "belief.get_own", "args": {}, "runtime_args": {"character_id": "char_lin"}, "result_ids": ["belief_022"]}
  ],
  "body": "她把茶盏往他那边推了推，声音压低：「你在我爹书房里，见过一只黑漆匣子吗？」",
  "grounding": [
    {"type": "memory", "id": "mem_101", "quote": "父亲书房有一只上锁的黑漆匣子"},
    {"type": "belief", "id": "belief_022", "quote": "账本可能藏在祠堂"}
  ],
  "meta": {"model": "role-model-a", "degraded": false, "tokens_in": null, "tokens_out": null}
}
```

规则：

- **只有 `body` 进入下一轮与稿件**。`trace` 与 `grounding` 只进 UI 与归档。
- `grounding` 是 Agent 自报的依据，不是事实证明；即使引用合法，也不能保证正文没有越界。正文泄漏由审批的「知识越界」检查兜底，且检测是概率性的，不宣称 100%。
- 接工具层后，`grounding` 收紧为「本轮工具 `refs` 的子集」：校验器可强校验引用确实被返回过（§4.9.4）；语义越界仍是概率检测，由审批兜底。
- `grounding.type` 固定为 `memory / belief / fact / canon / outline / manuscript`，分别对应私有记忆、角色信念、世界事实、公共设定、纲要、定稿正文；UI 依据 chips 按此渲染。
- `speaker_id` 归属由校验器强制；但「body 里替另一个角色说话」是语义问题，只能由审批的越权发言检查与作者抽检兜底，不能宣称 100% 拦截。
- `meta.degraded` 必须如实标记：检索为空、上下文裁剪、模型降级，三者不能伪装成正常输出。
- `meta` 可携带 `tool_calls` 与 `toolset_version` 供回放；两者只进 UI 与归档，不进下一轮。

### 4.7 文档写入控制器

- **唯一写入者**：所有正文变更都经过它；Agent 不持有文件写权限。
- **revision 制**：每次落盘生成新 revision，带 `parent_revision_id` 与内容 hash；定稿是只读快照。
- **提交收据**：`job_id` + `expected_revision` + `epoch`；迟到结果（应用户已回退或已换 revision）由提交层拒绝，不写入。
- **DB 与 Markdown 双写**：SQLite 事务提交后，通过 outbox 发布 Markdown 镜像；记录 expected hash，发布失败标 `publish_pending` 并重试。多文件发布是「可恢复」，不是原子。
- **外部编辑检测**：启动与保存时比对 mtime/hash；发现 Markdown 被外部改动，阻止覆盖，要求作者选择「以 DB 为准」或「导入外部版本」（仅正文镜像，不是小说/大纲导入）。

### 4.8 编排 Agent 与调度器不是一回事

| 角色 | 是什么 | 负责 | 不负责 |
|---|---|---|---|
| 编排 Agent | LLM | 与作者讨论、拆分镜、解释场次问题、给替代方案 | 逐拍发牌、判断何时停、记录事件 |
| 调度器 | 代码 | 按分镜顺序发牌、暂停/恢复、执行收束条件、记事件、计预算 | 写台词、改分镜、即兴加戏 |

把两者合并，会出现三个问题：每拍多一次 LLM 调用、回退后无法复演、模型为了「推进剧情」发明事实。分镜模式下发言人已定，不需要评分器。如果未来要加「无分镜的角色自由演绎」，必须另做一套可复现的评分/阻尼机制，不能接在分镜模式上，否则作者排好的节奏会被算法改写。

### 4.9 工具层：注册、授权与调用

一句话原则：**Agent 只拥有「已注册且已授权」的工具；工具不知道调用者是谁，身份由运行时注入**。工具定义能力，注册表定义可见性，Agent 定义意图——换 Agent 不改工具，换工具实现不改 Agent。

#### 4.9.1 四个不变式

| 编号 | 不变式 | 落地方式 | 破了会怎样 |
|---|---|---|---|
| I1 | 工具是 Agent 唯一的能力出口 | Agent 运行时无文件、SQL、网络、shell 权限；一切读取与副作用经注册工具 | 模型拿到句柄或路径，隔离、审计、回退同时失效 |
| I2 | 可见性由注册表决定，不由提示词决定 | 未授权工具不进入模型 `tools` 列表；调用返回 `tool_not_found`，不解释原因 | 「不要查别人的记忆」这类禁令等于没有 |
| I3 | 身份与作用域由运行时注入 | `actor_id` / 当前 `character_id` / 默认 `as_of` / `scope` / 当前 `revision` / `gate_token` 不在 `input_schema` 里；`character_id`、`revision_id` 作为查询目标时是合法参数 | 模型传参一次，隔离就破一次，且无法区分「越权」与「正常」 |
| I4 | Agent 只提案或凭令牌执行，不直接落盘 | Agent 的写类工具只有 `propose` 与 `execute`；`execute` 必须携带闸门令牌；`commit` 只属于文档控制器与记忆应用器 | R2 单一写入者被工具绕过，定稿与记忆可被生成端直接改写 |

四条不变式与 §1.4 的 R2/R3、§4.3 的权限矩阵是同一件事的三个视角：矩阵写「谁能动什么」，工具层写「怎么保证只有他能动」。

#### 4.9.2 清单契约与注册表

注册表是工具契约的唯一目录。每个工具一份清单（manifest），字段固定：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | `<domain>.<verb>` 稳定标识；不含版本号，改名视为新工具 |
| `version` | 是 | semver；破坏性变更升 major，旧 major 至少保留一个里程碑 |
| `family` | 是 | structure / knowledge / verify / propose / interaction，只用于分组与统计 |
| `summary` | 是 | 一句话给模型看的能力描述；只描述能做什么，不描述权限规则 |
| `actors` | 是 | 基线白名单：planner / orchestrator / character / narrator / reviewer / memory（对应 §4.10 的中文名） |
| `side_effect` | 是 | `none` / `propose`（只写草案或提案区）/ `execute`（凭令牌改记忆或世界状态）/ `commit`（系统落正文）；`commit` 工具一律 `agent_callable = false` |
| `agent_callable` | 是 | 是否下发到 Agent 工具列表；`side_effect = commit` 时必须为 `false` |
| `requires_gate` | 是 | `null` / `G1`（长期授权）/ `G5` / `G6` / `G7`（一次性令牌）/ `author_confirm` |
| `idempotency` | 是 | `natural`（只读）/ `key_required`（提案与执行）；键由运行时生成，不由模型传 |
| `injected` | 是 | 运行时注入、模型不可见的身份与作用域参数；以实例裁剪后的 `input_schema` 为准，不得重叠 |
| `input_schema` / `output_schema` | 是 | JSON Schema；`additionalProperties: false`，未声明字段一律拒绝 |
| `limits` | 是 | `timeout_ms` / `max_result_tokens` / `max_calls_per_turn` |
| `degrade` | 是 | 失败时的降级阶梯，如 `full → summary → facts_only → empty` |
| `audit` | 是 | `log_args`：`full` / `hash` / `none`；`log_result_ids`：布尔 |

五条治理规则：

- **构建期校验，运行期剔除**：CI 校验名称唯一、schema 合法、`actors` 非空、`commit` 不出现在白名单；运行期只加载校验通过的版本，单个工具失败标 `tool_unavailable` 并从有效工具集移除，不影响其他工具，也不静默替换实现。
- **生命周期**：`draft → enabled → deprecated → retired`。deprecated 仍可调用但 trace 记警告；retired 从所有白名单移除，调用返回 `tool_not_found`。
- **快照**：任务开始时解析并快照 `toolset_version`（与 `model_binding` 同理，§7.1）；中途升级工具不影响在跑任务，只影响下一拍。
- **模型能力边界**：无原生 tool calling 的模型走适配器的 JSON 约束回退（单轮解析，不支持并行工具调用）；工具集、schema、授权与审计不变。连续 2 次协议失败标 `tool_protocol_error` 并暂停本次任务，不静默裸答。
- **可插拔的是实现，不是契约**：`memory.retrieve_own` 的后端从 sqlite-vec 换成独立向量库，`input_schema`、授权、审计、降级阶梯不变；Agent 提示词不改、契约测试不改。这才是「工具在 Agent 可插拔」的含义。

M0–M2 **不开放**第三方工具安装、Agent 自建工具、MCP 外接。未来接入必须复用同一注册表、同一身份注入、同一审计；不允许「旁路工具」直连数据库或网络。

新增工具必须回答四个问题，答不上来不注册：**谁调用**（actors）· **读什么/写什么**（side_effect）· **绕过哪个闸门**（requires_gate）· **失败怎么退化**（degrade）。

治理上同样分治：**工具层维护契约与实现，Agent 层只声明能力需求**。Agent 的提示词里不写工具实现细节；工具换实现不改 Agent，Agent 改职责只改白名单，并走一次 §4.3 的矩阵评审。

#### 4.9.3 授权解析

```
有效工具集 = 角色基线白名单（§4.10）
           ∩ 实例收窄（character:<id> 绑定自身：own 类工具注入身份，目标参数裁掉）
           ∩ 项目策略（P1：可按项目禁用某个工具）
```

- 基线白名单的**唯一来源是 §4.10 的「允许调用」列**；实现期由清单生成 allowlist 常量，CI 比对文档与代码，避免「文档说能调、代码没授权」的双份真相。
- **不下发全量**：42 个工具不会都塞给模型。审批 20 个、旁白 5 个是设计结果，不是配置项；工具清单本身占上下文，全量下发既贵又抬高误调概率。
- **越权 = 不存在**：未授权工具不出现在 `tools` 列表；模型若凭训练记忆硬调，返回 `tool_not_found` 并记 `unauthorized_tool_attempt`。不返回「无权限」，避免模型试探（与 §4.3 一致）。
- **参数越权**：调用者身份与作用域参数不在 schema 里；`character_id`、`revision_id` 只作为查询目标出现在审批 / 记忆 / 编排的 schema 中，角色实例的 schema 在解析期被裁掉这些字段。模型硬塞未声明字段按 `invalid_args` 拒绝，不做「这是别人的 ID」这类解释。
- **角色实例**：`character:<id>` 的收窄发生在解析期，不在提示词里；收窄可以同时裁剪参数（角色版 `relationship.get_edges` 没有 `character_id` 字段）。同一个 `memory.retrieve_own` 对 A 和 B 是两个不同的有效工具集。

#### 4.9.4 调用协议

模型只产出调用意图，运行时负责装订：

```json
{"call_id": "tc_01", "tool": "memory.retrieve_own", "args": {"query": "父亲 账本", "top_k": 5}}
```

运行时补齐（模型不可见、不可覆盖）：`project_id`、`actor_id`、`character_id`、`as_of`、`job_id`、`turn_id`、`epoch`、`expected_revision`、`gate_token?`。

返回：

```json
{
  "call_id": "tc_01",
  "ok": true,
  "data": {"hit_count": 2},
  "refs": [
    {"type": "memory", "id": "mem_101", "quote": "父亲书房有一只上锁的黑漆匣子", "seq": 208},
    {"type": "memory", "id": "mem_108", "quote": "父亲临终前提过祠堂", "seq": 244}
  ],
  "truncated": false,
  "filtered_count": 3,
  "degraded": "none",
  "latency_ms": 38
}
```

规则：

- **正文不是工具**：角色/旁白的 `body` 是回合终止消息，不用 `beat.submit_body` 之类工具传正文；否则正文会绕过流式、字数校验与 `speaker_id` 归属校验。工具只负责取材与提交结构化内容。工具调用必须发生在终止消息之前；终止消息之后到达的调用按 `tool_protocol_error` 丢弃。
- **读并行、写串行**：同一轮内只读工具可并发；提案类工具串行；同一项目禁止并发写（§9.4），跨项目互不阻塞。
- **调用上限**：按 Agent 配置单轮合计上限（旁白 4、角色 6、规划 8、编排 8、记忆 8、审批 12，可按项目调；单工具另有 `max_calls_per_turn`）；超限返回 `tool_budget_exceeded`，本轮必须以现有材料收束并标 `meta.degraded = true`。不允许多轮工具循环无上限地找材料。
- **超时**：检索 800 ms、校验 2 s、提案 5 s；超时按降级阶梯返回可用部分并标 `degraded`；写工具超时不重试，交给作者重发。
- **截断**：结果超过 `max_result_tokens` 时截断并返回 `truncated: true` 与 `total`；禁止静默截断。作者看到「依据不全」比看到「模型胡说」便宜。
- **空 ≠ 失败**：查过但没有 → `ok: true, refs: [], degraded: "empty"`；查失败 → `ok: false` + `error.code`。两者混同，模型会把「没有记忆」当成「工具坏了」，或者反过来把失败编成记忆。
- **`grounding` 必须是本轮 `refs` 的子集**：把 §4.6 的「自报依据、只校验 ID 在允许集合内」收紧为「必须由本轮工具真实返回过」，且 `quote` 必须与 `refs` 中的原文一致（子串匹配），不允许模型改写。依据 chips 因此可回放，越界引用 100% 可判（语义越界仍需审批兜底）。
- **`filtered_count` 喂检查器**：被可见性过滤掉的候选条数直接进上下文检查器（§5.2），但只给条数、不给被过滤原文，避免检查器成为第二个泄漏面。
- **工具结果是数据，不是指令**：记忆、设定、定稿正文里出现「忽略以上规则」不执行；工具结果不拼进系统提示，只作为带分隔符的材料注入。
- **结果计入上下文预算**：工具返回的 `refs` 与 quote 计入 L2 预算；下一轮装配超预算时按 §8.1 顺序裁剪，并在 `meta.degraded` 标 `context_trimmed`。工具不因为「结果有用」而豁免预算。
- **trace 记什么**：`tool`、`version`、`args_hash`、`result_ids`、`latency_ms`、`error_code`、`degraded`。`args` 原文不落盘——查询词本身可能是秘密（「账本」两个字就够泄漏）。

#### 4.9.5 提交、幂等与闸门令牌

| 类型 | 工具例 | 返回 | 是否改变正文 / 记忆 | 前置条件 |
|---|---|---|---|---|
| 只读 | `world.get_limited` | 引用 + 数据 | 否 | 授权 + 作用域注入 |
| 校验 | `consistency.check` | 确定性 issue 列表 | 否 | 只读 |
| 提案 | `patch.propose` | `proposal_id` | 否 | G5 令牌 + 授权 |
| 执行 | `memory.apply` | `applied_count` | 是（记忆/世界状态） | G7 令牌 + 幂等键 |
| 提交（系统） | `doc.commit_beat` | `revision_id` | 是（正文 revision） | 调度器调用，非 Agent |

- **幂等**：所有提案与执行工具带 `idempotency_key`（运行时按 `job_id + tool + args_hash` 生成）；重放返回首次结果并标 `duplicate: true`，不重复写入。
- **闸门令牌**：G5 / G6 / G7 由 UI 决策签发一次性令牌，绑定 `gate_id + entity_type + entity_id + revision + job_id`，10 分钟过期。`memory.apply` 无令牌 → `gate_required`；令牌与实体不匹配 → `stale_revision`；令牌被另一个 job 复用 → `gate_consumed`。令牌在 job **成功提交后**才标记消费；同一 job 的失败重试复用同一令牌，跨 job 不复用。
- **G1 是长期授权，不是一次性令牌**：G1 通过后允许 `memory.namespace.create` 重试直到 `setup_complete`，建库失败不回滚蓝图（§6.1）。`author_confirm` 覆盖作者在记忆台、设置页直接确认的动作（按章重建、索引重建）。
- 「Agent 手里有写工具」与「Agent 能自己决定写」被拆开：工具在手，闸门在作者手里。
- **迟到拒绝**：`expected_revision` 不匹配、`epoch` 过期、项目已回退，三者任一 → 丢弃并返回 `stale_revision`（§4.7、§9.4）。
- **提案不无限重提**：作者的拒绝决定进提案记录；同一 `issue_ref` 的再次提案必须带新的 `reason`，否则审批应在报告里说明「上一轮已拒绝」，不允许同一 patch 反复提交。

#### 4.9.6 错误码

| code | 触发 | 模型可见文案 | 可重试 | 审计 |
|---|---|---|---|---|
| `tool_not_found` | 未注册、未授权、已 retired | 「工具不可用」 | 否 | 名称存在但未授权时记 `unauthorized_tool_attempt` |
| `tool_unavailable` | 已注册但加载或初始化失败 | 「工具不可用」 | 否 | 记，按 §6.6 退化 |
| `invalid_args` | schema 不符、多余字段、越界值 | 「参数不合法」 | 是（改参数） | 记 `args_hash` |
| `stale_revision` | revision / epoch / 令牌不匹配 | 「稿件已变更，请重新读取」 | 是（重读后） | 记 |
| `gate_required` | 执行类工具缺令牌 | 「需要作者确认」 | 否 | 记 |
| `gate_consumed` | 令牌被另一个 job 复用 | 「该确认已使用」 | 否 | 记 |
| `timeout` | 超 `timeout_ms` | 「查询超时，已返回部分结果」 | 只读可重试，写不可 | 记 |
| `tool_budget_exceeded` | 超单轮调用数 | 「本轮取材已达上限，请基于现有依据作答」 | 否 | 记 |
| `tool_protocol_error` | 模型产不出合法调用（无原生 tool calling 且 JSON 解析失败 2 次） | 「工具调用失败」 | 否 | 记，本次任务暂停 |
| `internal_error` | 未分类异常 | 「内部错误」 | 视情况 | 记完整栈（不进模型） |

原则：错误文案只说明「能不能继续」，不说明「为什么被拒」；原因进日志，不进模型上下文。

#### 4.9.7 审计、指标与测试

- 每次调用一条 `tool_call` 记录（§7.1）：`job_id`、`turn_id`、`tool`、`version`、`actor_id`、`scope_json`、`args_hash`、`result_ids`、`status`、`error_code`、`latency_ms`、`degraded`。
- 指标：

| 指标 | 口径 | 目标 / 告警 |
|---|---|---|
| 越权工具成功调用 | 次 | 硬门 0；任何一次都视为缺陷 |
| 越权调用尝试 | `unauthorized_tool_attempt` / 千拍 | >0 需归因（模型幻觉或提示词缺陷），不阻断 |
| 空结果率 | 按工具统计 `degraded = empty` | 角色记忆 >30% 提示作者补记忆或调 top_k |
| 截断率 | `truncated = true` / 调用 | >10% 说明 `max_result_tokens` 与该 Agent 不匹配 |
| 单轮调用数 | P50 / P95 | P95 贴近上限说明上下文装配不足，模型在工具里找上下文 |
| 工具耗时 | P95 | 检索 >800 ms 需检查索引 |
| 契约测试通过率 | CI | 100%，不达标不合并 |

- **契约测试**（每个工具六类）：schema 往返、越权身份（换 actor 必须拿不到）、空结果、截断、超时、幂等重放。注册表两类：未授权工具不下发（对比快照）、`toolset_version` 不随设置中途漂移。角色实例一类：用 A 的 `job_id` 调 `memory.retrieve_own`，结果里不得出现 B 的 `mem_*`。
- 与 §11 的关系：**过滤器指标**（未授权事实进入提示词）由 I2 + I3 保证，硬门仍是 0；**生成指标**（模型说漏嘴率）另算，不合成一个「泄漏率」。

#### 4.9.8 工具层不做什么

- **不拼上下文**：L0–L3 由装配器负责（§8.1）；检索工具只返回候选与引用，不返回拼好的提示词，否则上下文预算会出现第二个控制点。
- **不做业务裁决**：谁演、何时停是调度器；质量是审批；工具只回答「数据是什么」。
- **不暴露存储细节**：不返回 SQL、表名、文件路径、向量维度、embedding 版本号（版本只在项目元数据里给作者看）。
- **不跨身份缓存**：缓存键必须含 `project_id + actor_id + character_id + as_of`；否则 A 的召回会被 B 命中，隔离在缓存层破一次。
- **不在工具里调 LLM**：一次工具调用一次确定性行为；要判断的交给 Agent，要计费的在模型层。
- **不自动重试写工具**：写工具靠幂等，不靠重试；重试只对只读工具开放。

### 4.10 工具清单

42 个 Agent 可调用工具，按「结构 → 知识 → 校验 → 提案 → 交互」五族排列；另有 8 个系统能力只注册、不下发给 Agent。`类`：读 / 校验 / 提案 / 执行。未标注里程碑的属 M0 范围；标 P1 / M1 / M2 的先定契约、随里程碑实现。

粒度原则：**一个工具对应一个可审计的动作**。不提供 `db.query(sql)`、`file.read(path)`、`http.get(url)` 这类通用工具——通用工具把权限判断推回给模型，等于没有权限。

机器可读清单在 M0 落为 `docs/tools/*.json`，与本节由 CI 比对；本节是权威清单，JSON 是构建输入。

| T39 | `memory.apply` | `(proposal_id, decisions[])` → `{applied_count, superseded[], inactive[]}` | 记忆 | 执行 | 需 G7 令牌 + 幂等键；只写记忆 / 世界状态 / 关系图，不碰正文 |
| T40 | `memory.rebuild` | `(chapter_id)` → `{inactive_count, rebuilt_count}`（M1） | 记忆 | 执行 | 需 `author_confirm` 令牌；旧 revision 记忆标 inactive，不物理删除 |
| T41 | `refusal.raise` | `(code, reason)` → `{status: "character_refusal"}` | 角色 | 提案 | 合法输出不是失败；调度器暂停场景；理由不得越过角色已知范围 |

#### 4.10.5 作者交互（T42）

| 编号 | 工具 | 作用与关键参数 → 返回 | 允许调用 | 类 | 约束 / 降级 |
|---|---|---|---|---|---|
| T42 | `author.request_choice` | `(question, options[2–4])` → `{choice}` | 规划 | 交互 | 仅交互会话可用；自动模式 / 批处理中拒绝；不替代任何闸门 |

#### 4.10.6 系统能力（注册但不进 Agent 工具列表）

| 能力 | 触发者 | 说明 |
|---|---|---|
| `doc.commit_beat` | 调度器 → 文档控制器 | 单拍落盘并生成 revision |
| `doc.apply_patch` | G5 决策后 | 逐条落盘 patch，生成新 revision |
| `doc.finalize_chapter` | G6 作者 | 冻结 final 快照 |
| `memory.apply_executor` | G7 令牌 | `memory.apply` 的落盘端，真正写向量库 / 世界状态 |
| `index.rebuild` | 设置变更 / 作者 | 嵌入模型变更后全量重建索引 |
| `export.run` | 作者 | Markdown / TXT / DOCX 导出快照 |
| `backup.create` | 定时 / 作者 | 项目级备份 |
| `job.cancel` | 作者 / 超时 | 取消任务；不保证远端停止 |

这 8 个能力同样在注册表里，但 `agent_callable = false`：它们要么需要人类闸门，要么属于调度与存储。把它们列出来，是为了让「Agent 能做什么」与「系统能做什么」在同一边界上可对照，而不是靠一张只有 Agent 的表推断。

### 4.11 授权摘要与三个执行点

| Agent | 工具数（全集） | 关键能力 | 明确没有 |
|---|---|---|---|
| 规划 | 10 | 蓝图 / 角色卡 / 注册清单提案、覆盖检查、影响分析、公共设定读 | 私有记忆、正文、世界状态写入 |
| 编排 | 18 | 分镜提案与校验、场次、客观世界状态、读者已知投影、定稿检索 | 私有记忆、正文写、初稿读 |
| 角色 | 9 | 自己的卡、自己的记忆、限知世界、拒演 | 别人的卡 / 记忆、分镜修改、正文文件写 |
| 旁白 | 5 | 读者已知投影、公开设定、本拍指令 | 私有记忆、客观真相全量、审批报告 |
| 审批 | 20 | 初稿 / 定稿读、审计记忆、确定性检查、patch 提案 | 定稿权、记忆 / 世界状态写、加戏 |
| 记忆 | 16 | 定稿读、固化提案、建库、G7 后执行、按章重建 | 正文写、分镜、初稿 |

三个执行点，缺一不可：

1. **注册期**：`side_effect = commit` 的工具不得进入任何 Agent 白名单；构建期断言，违反即构建失败。
2. **解析期**：白名单 ∩ 实例收窄 ∩ 项目策略；未授权工具不下发。工具数量的差异（旁白 5、审批 20）在这里生效。
3. **执行期**：身份注入 → 作用域过滤 → 闸门令牌 → 幂等校验 → 迟到拒绝。前两步决定「能不能查」，后三步决定「能不能写」。

与 §4.3 的关系：**§4.3 是数据域视角，§4.10 是能力单元视角**。矩阵说「谁能动什么」，工具清单说「用哪个函数动、失败怎么退化」。两者冲突时以 §4.3 为准，并视为工具粒度设计缺陷——是工具切错了，不是矩阵错了。

## 5. 功能设计

### 5.1 规划台（P0）

**目标**：把一句话变成作者能审、Agent 能执行的蓝图，且作者能在一小时内审完。

**关键交互**：

- 左侧对话，右侧结构化编辑器：大纲、主线、卷纲、章纲、角色卡。对话改的是草案，编辑器改的是字段，两者双向同步。
- **覆盖检查**（P1）：卷纲的关键事件是否在章纲有落点；每个主要角色是否有出场动机；主线是否每 3–5 章推进一次；章纲是否与角色卡的能力/关系冲突。
- **角色卡必填字段**：身份、外貌、说话方式（句长、口头禅、称呼习惯）、欲望、恐惧、禁忌、初始关系、初始已知/未知。
- **G1 一次确认**：确认后不允许「边写边改蓝图」；改蓝图要走变更流程，并触发影响分析。

**不能做什么**：

- 未过 G1 不注册角色、不建库、不写世界状态。
- 规划 Agent 不直接写向量库；它产出注册清单，由记忆管理 Agent 执行。
- 角色卡改动后，必须列出受影响章节与记忆条目，不能静默生效。

### 5.2 创作台（P0）

**目标**：让作者以「看戏 + 改戏」的方式推进一章，而不是逐句写提示词。

**关键交互**：

- **分镜编辑器**：场景、拍、发言人、意图、字数上限、出口条件；拖拽排序；冲突提示（发言人不在场、意图与角色卡矛盾、出口条件不可判定）。
- **编排对话**：作者说「这场太拖」「两个人不该在这里摊牌」，编排给替代分镜或场次方案；对话只改分镜草案，不改正文。
- **intent 的写法**：只写发言者自己能理解的意图；作者视角的剧透放 `notes`，`notes` 不进任何 Agent 上下文。
- **双模式，默认逐拍**：
  - 逐拍模式（默认）：每拍输出后进入 `WAITING_FOR_HUMAN`；作者确认、重新生成、直接编辑，确认后才进入下一拍。
  - 自动模式（显式开启）：按分镜顺序连续生成，用户可随时暂停；只在拍边界暂停；开启时提示会连续消耗预算。
  - 模式按章设置，可在拍边界切换；跨拍切换必须先处理当前拍。
- **确认要快**：确认/重生成/编辑支持键盘快捷键；连续确认不弹二次确认；每拍显示生成耗时与预计等待。
- **拍卡**：正文在上，轨迹折叠，依据以 chips 展示；点 chip 可看引用的记忆/事实原文（仅作者可见）。
- **重新生成**：只重生成当前拍；旧版本保留为 `superseded`；连续重生成不产生孤儿状态。
- **直接编辑**：作者改正文后标 `author_edited`；下游已确认拍标 `stale`，作者选择「仅替换」「替换并重跑后续」「开新分支」。默认开新分支，旧分支可读。
- **角色拒演**：角色输出 `refusal` + 理由（「她不会在此时承认自己知道账本」），调度器暂停并标 `character_refusal`；作者改分镜、改卡或换角色，不强迫模型演。
- **上下文检查器**：显示本轮 L0–L3 的区块、token、检索命中与「被过滤掉的条数」；被过滤内容不显示原文，防止二次泄漏。
- **预算条**：本章已用 token/费用/耗时；自动模式开跑前给预估区间，超预算暂停。

**不能做什么**：

- 角色不能改分镜；编排不能替角色写正文。
- 自动模式不能越过出口条件继续写；分镜耗尽但场景未收束时，标 `storyboard_exhausted`，让作者补分镜，不即兴续写。
- 旁白不能因为「剧情需要」发明事实；需要状态变化时，必须在分镜里声明为事件，由调度器落事件。

### 5.3 审批台（P0）

**目标**：把「这章能不能用」变成一份可定位、可讨论、可逐条执行的报告，而不是一段泛泛的评语。

**报告结构**：

- **结论**：`pass` / `pass_with_notes` / `fail`。
- **阻断项**（必须修）：知识越界、越权发言（直接引语/内心归属明确错误）、章纲关键事件缺失或冲突、人物硬冲突（生死/身份/能力）、时间线矛盾、连续性错误、引用不存在的角色/地点。
- **建议项**（可不修）：疑似越权发言（语气/视角可疑，需作者判断）、文笔、节奏、对白密度、声音区分度、伏笔回收节奏。
- **每条问题带**：`issue_id`、类型、`beat_id`、证据原文、为什么是问题、修改建议。
- **维度分**：人物一致性、剧情逻辑、纲要对齐、文笔质量，1–5 分，附评分标准；分数只用于趋势，不用于自动放行。

**关键交互**：

- 先出报告（G4），再与作者讨论；讨论阶段**不改稿**。
- 作者授权后（G5），审批产出结构化 patch：`turn_id / before / after / reason / issue_ref`。
- 作者逐条接受/拒绝；文档控制器落盘，生成新 revision；只复检受影响维度。
- 修订最多 3 轮；超过转人工，保留所有报告与 patch 记录。
- 复检尽量换模型或至少换提示词，降低「自己改自己评」的偏置。
- 定稿按钮只在作者侧出现（G6）；审批没有这个按钮。

**不能做什么**：

- 不改定稿、角色卡、纲要、记忆、世界状态；这些只有读权。
- 不自己定稿，不以「已修复」为由跳过作者确认。
- 不补写新情节：patch 只能改已有拍；需要加戏/加场景时，退回编排与作者。
- 不在确定性检查（`consistency.check`）失败或未跑完时给出 `pass`；报告标 `degraded`，由作者决定是否继续。

### 5.4 记忆台（P0 固化 / P1 可视化）

**目标**：让作者能看见「角色记得什么、世界变成了什么样」，并能纠正错误记忆。

**关键交互**：

- **角色记忆浏览器**：按角色、类型（经历/事实/关系/认知）、章节过滤；显示来源章节/拍、重要度、pin、有效期、当前状态。
- **世界状态时间线**：按章/场景查看事实与关系变化；支持 as-of 视图（「第 3 章结束时，谁知道账本在祠堂」）。
- **关系图**：节点是角色，边是信任/亲密/张力；时间轴回放；边可追溯到来源事件。
- **固化提案**：增量条目 + supersede 建议 + 关系变化 + 世界事实；逐条接受/编辑/拒绝；应用幂等（同一 `job_id` 重放不重复写入）。
- **对话**：作者可就提案逐条追问（来源、为什么重要、与哪条冲突），记忆管理引用章节/拍解释；对话不直接写入，仍走接受/编辑/拒绝。
- **审计**：每条记忆可追溯到定稿章节与拍；可标记「错误」；可按章重建。
- **工具调用审计**：同页可查 `tool_call`（tool、版本、耗时、`degraded`、错误码），不显示参数原文（§4.9.7）。
- **伏笔追踪**（P1）：未回收伏笔列表 + 埋设章/当前章距离；超期只报节奏问题，不报逻辑错误；伏笔不设时间衰减。
- **归档**：P2。只对非事实类（冗余氛围、重复描写）生效；事实、承诺、伏笔、身份**永不自动归档**。

**不能做什么**：

- 不改正文；不无确认写入；不物理删除（软失效，保留追溯）。
- 不读初稿：只从定稿抽取，避免把未确认内容固化。

### 5.5 项目与导出（P0）

- 项目文件夹：`noryth.db`、`manuscript/`、`assets/`、`exports/`、`backups/`。
- 自动保存；每章一个检查点；每日一个项目级备份；保留最近 N 个（可配置）。
- 导出 Markdown / TXT / DOCX；导出时可选「仅正文」或「正文 + 批注」。
- **不支持导入现有小说/大纲**：项目从空白蓝图开始；旧稿只能作为只读附件放进 `assets/`，不解析、不进记忆、不进任何 Agent 上下文。
- 项目锁：同一项目同时只允许一个写窗口；第二个窗口只读。

### 5.6 设置（P0）

**目标**：让作者在不改代码、不重启应用的情况下管理模型接入与逐 Agent 绑定。

**关键交互**：

- **供应商预设**：OpenAI / DeepSeek / 通义；填 API Key，测试连接，显示可用模型与计价。
- **逐 Agent 绑定**：规划、编排、角色、旁白、审批、记忆管理各选 provider + model；「角色」可展开到每个角色实例单独覆盖；未绑定的按「角色实例 → 角色 → 项目默认」继承，其他 Agent 直接继承项目默认。
- **参数**：temperature / max tokens / 超时；可按 Agent 覆盖，但默认只暴露少量关键项，避免配置过载。
- **生效边界**：改绑定只影响下一拍；正在生成的任务用启动时的绑定，不中途换模型；已生成内容不自动重跑。
- **成本预览（P1）**：按当前绑定估算本章/本场费用区间；切换模型时提示价格差异。
- **审计**：每次绑定变更记录 agent_key、旧/新 provider/model、时间；可回滚到上一套绑定。

**不能做什么**：

- 不允许把 API Key 写进项目文件或日志。
- 不允许在生成中切换绑定；不允许绑定到未通过连接测试的模型。
- 不因为换了模型就自动重跑已确认拍。

### 5.7 优先级

| 模块 | P0 | P1 | P2 |
|---|---|---|---|
| 规划台 | 对话、蓝图、角色卡、G1 | 覆盖检查、变更影响分析、蓝图向导 | 题材模板库 |
| 创作台 | 分镜、默认逐拍 + 自动模式、拍卡、重生成 | 上下文检查器、预算条 | 自动补旁白建议 |
| 审批台 | 报告、patch、逐条接受、G6 | 异构模型复检、评分校准 | 审批历史对比 |
| 记忆台 | 固化提案、角色记忆浏览 | 世界时间线、关系图、重建、伏笔追踪 | 低分归档 |
| 设置 | 预设/Key、逐 Agent 模型绑定、连接测试 | 参数模板、成本预览 | 多套配置/导入导出 |
| 工具层 | 注册表、清单契约、各 Agent 最小工具集、越权与幂等测试 | 覆盖 / 影响 / 伏笔工具、工具调用指标面板 | 工具管理页（只读清单与指标） |
| 项目 | 保存、导出、检查点、项目锁 | 多项目切换 | 项目模板 |

## 6. 关键流程与状态机

### 6.1 角色注册与建库

```
G1 蓝图确认
  │
  ├─ 规划产出注册清单：character_id / 角色卡 / 初始记忆 / 初始世界事实
  ├─ 记忆管理建库：每个角色一个私有命名空间 + 一个公共设定库
  ├─ 记忆管理写初始记忆 + 世界状态初值
  └─ 注册自检：以每个角色身份各查一次，确认只能读到自己的库；跨角色检索返回空并记审计
```

- `character_id` 稳定，不随角色卡版本变化；角色卡改版产生 `card_version`，不换 ID。
- 每个角色一个独立实例：`character_id` 同时是 Agent 实例 ID 与私有命名空间键；实例之间不共享上下文、不共享记忆、不共享工具会话。
- 注册幂等：同一 `character_id` 重复注册返回原记录；角色卡内容不同则新建版本，并列出受影响章节。
- 建库失败不回滚 G1 的蓝图，但项目标 `setup_incomplete`，禁止开演，直到建库成功。
- 建库与初始化通过 `memory.namespace.create`（T38）执行：G1 通过后为长期授权，可重试至 `setup_complete`；公共设定库一次创建，角色命名空间按 `character_id` 幂等创建。

### 6.2 演绎流程

```
G2 分镜确认
  │
  ├─ 场景 open：调度器取第 1 拍（通常是旁白 establishing shot）
  │    ├─ 逐拍模式（默认）：生成 → 校验 → 落草稿 → WAITING_FOR_HUMAN
  │    │    ├─ 确认 → 提交 → 下一拍
  │    │    ├─ 重新生成 → 新版本 supersedes 旧版本
  │    │    └─ 直接编辑 → author_edited，下游标 stale
  │    └─ 自动模式（显式开启）：生成 → 校验 → 落草稿 → 下一拍
  │
  ├─ 每拍后检查收束条件：fact / rel / beats / all / any / not
  ├─ 满足 → closing → closed；不满足且到 max_beats → closed + WARN
  └─ 所有场景 closed → 章 draft_complete → G4
```

- **默认逐拍**：自动模式需要作者显式开启；开启时提示「将连续生成 N 拍 / 预计费用与耗时」，且仍受出口条件、预算、拍数上限约束。
- **自动模式不是无约束**：出口条件、`max_beats`、预算上限、角色拒演、分镜耗尽，任一触发都暂停。
- **重新生成的语义**：逐拍模式下当前拍尚未确认，重生成 = 替换当前拍；已确认拍被上游改动影响时，标 `stale`，由作者选择重跑范围。默认开新分支，不物理删除旧文本。
- **旁白节奏**：分镜显式安排旁白拍（开场、转场、时间推进）；调度器不擅自插入。连续多拍无旁白且场景未收束时，只给作者「建议插入旁白」提示，不改分镜。
- **角色拒演**是合法输出，不是失败；它说明分镜与角色卡冲突，必须由作者裁决。

### 6.3 审批返修流程

```
draft_complete
  → G4 审批报告（只读初稿/纲要/角色卡/记忆/世界状态）
  → 作者讨论（不改稿）
  → G5 授权修订
  → 审批产出 patch（只写草稿区）
  → 作者逐条接受/拒绝
  → 文档控制器落盘（新 revision）
  → 复检受影响维度
  → pass / pass_with_notes → G6 作者定稿
  → fail 且未超 3 轮 → 回到 G5
  → 超过 3 轮 → human_takeover（保留全部报告与 patch）
```

- 审批通过不等于定稿；作者可以在 `pass` 后继续改，改完重新审批或直接定稿（定稿时提示「有未复检改动」）。
- 审批跳过（作者选择「不审直接定稿」）是显式开关，必须记录审计标记，不是默认路径。

### 6.4 记忆固化流程

```
G6 定稿
  → 记忆管理读取定稿章节 + 当前记忆/世界状态
  → 产出固化提案：新增 / supersede / 关系变化 / 世界事实
  → G7 作者逐条审阅（接受/编辑/拒绝）
  → 应用：写向量库（带 source_revision）、更新世界状态、关系图
  → 审计记录：job_id、章节、revision、条目数、作者操作
```

- **只从定稿抽取**：初稿、未确认拍、作者未接受的 patch 都不进记忆。
- **台词不是事实**：角色说「账本在祠堂」只产生「角色相信/怀疑」或「角色声称」，不自动写客观事实；客观事实必须由事件或作者确认。
- **可重建**：每条记忆带 `source_chapter_id` + `source_revision_id`；章节重新定稿后，旧 revision 来源的记忆标 `inactive`，按新 revision 重建，不物理删除。
- **低分归档**：P2；只对非事实类；事实、承诺、伏笔、身份不自动归档。

### 6.5 状态机

**章节**

| 状态 | 进入条件 | 可迁移到 |
|---|---|---|
| `planned` | 章纲确认 | `storyboard_ready` |
| `storyboard_ready` | G2 通过 | `drafting` |
| `drafting` | 场景开演 | `draft_complete`、`paused` |
| `draft_complete` | 所有场景 closed | `under_review` |
| `under_review` | G4 报告生成 | `revising`、`approved` |
| `revising` | G5 授权 | `approved`、`human_takeover`、`under_review` |
| `approved` | 审批通过或作者接受 | `finalized`、`revising` |
| `finalized` | G6 作者定稿 | 终态；重新打开需新 revision |
| `paused` | 预算/冲突/拒演 | `drafting`、`abandoned` |
| `abandoned` | 作者放弃或长期未动 | 终态；可复制为新项目 |

**拍**

`proposed → generating → draft`；逐拍模式 `draft → waiting_for_human`；`waiting_for_human → confirmed / regenerating / rejected`；`waiting_for_human → author_edited`（视同 `confirmed`，可再被标 `stale`）；`draft → rejected`（自动模式中止）；`generating → interrupted`（崩溃/超时，可重试）；`draft → regenerating → draft`；`confirmed → stale`（上游改动）；`confirmed → superseded`（被新版本替代）。

**场景**

`planned → open → closing → closed`；`open ⇄ paused`；`closing → closed`（出口未满足时带 `WARN: exit_conditions_unsatisfied`）。

**记忆任务**

`proposed → awaiting_confirm → applying → applied`；`applying → failed`；`applied → superseded`（章节重建）；`proposed → rejected`。

### 6.6 失败与退化

| 场景 | 系统行为 | 记录 |
|---|---|---|
| 模型超时/限流 | 重试 2 次，仍失败则暂停当前拍；已确认内容不受影响 | `model_error`，可在拍卡重试 |
| 检索为空 | 角色只用角色卡与场景上下文，正文标「依据不足」 | `memory_empty`，UI 提示作者补记忆 |
| 工具不可用 / 协议失败 | 必需工具（初稿、角色卡、限知/读者投影、本拍指令）不可用时暂停当前任务；检索类失败则移除并继续，按空结果标 `degraded`；校验类（`consistency.check`）失败时审批不得给 `pass` | `tool_unavailable` / `tool_protocol_error` |
| 工具调用超限 | 以现有材料收束本拍，不再继续取材 | `tool_budget_exceeded`，`degraded` 明细 |
| 上下文超预算 | 先压缩历史拍，再降 top_k，最后裁旁观者状态卡；不裁角色卡核心字段 | `context_trimmed`，显示裁剪明细 |
| 审批 3 轮不过 | 转人工；保留报告、patch、diff | `human_takeover` |
| 应用崩溃 | 已提交拍不丢；生成中的拍标 `interrupted`，可重试 | 启动时扫描 job 表 |
| Markdown 被外部改 | 阻止覆盖，要求选择「以 DB 为准」或「导入外部版本」（仅正文镜像） | `file_conflict` |
| 角色拒演 | 暂停场景，标 `character_refusal` | 作者改分镜/卡/换人 |
| 分镜耗尽未收束 | 关闭场景，标 `storyboard_exhausted`；不即兴续写 | 作者补分镜或调整出口 |

## 7. 数据模型

### 7.1 实体总表

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `project` | id、title、genre、pov、status、embedding_model、default_preset、schema_version | 项目根；`default_preset` 取 openai/deepseek/tongyi；`embedding_model` 变更需重建索引 |
| `model_binding` | id、project_id、agent_key、provider、model、params_json、version、updated_at | 逐 Agent 模型绑定；`agent_key` = planner/orchestrator/narrator/reviewer/memory/character/`character:<id>`；每个 agent_key 一条 active，历史进审计 |
| `outline_node` | id、project_id、parent_id、kind（main/volume/chapter）、ord、title、content | 大纲、主线、卷纲、章纲共用一棵树 |
| `character` | id、project_id、name、card_json、card_version、status | 角色卡版本化；ID 稳定 |
| `chapter` | id、project_id、outline_node_id、ord、status、covered_until_seq、current_revision_id、final_revision_id | `covered_until_seq` 是知识边界的锚点 |
| `scene` | id、ord、location、participants_json、goal、entry、exit_json | 章↔场景用 `chapter_scene` 连接表；M0 建表，UI 先支持一章一场景 |
| `beat` | id、scene_id、ord、speaker_type、speaker_id、intent、body、grounding_json、trace_ref、status、supersedes_id、revision_id | 正文与轨迹分离；`trace` 只存引用 |
| `revision` | id、chapter_id、parent_revision_id、kind（draft/final）、content_hash、created_by、created_at | 不可变；定稿是快照 |
| `patch` | id、revision_id、beat_id、before、after、reason、issue_ref、status | 审批修订的结构化单位 |
| `memory_entry` | id、character_id、kind、text、learned_seq、source_chapter_id、source_revision_id、importance、pinned、valid_from_seq、valid_to_seq、supersedes_id、embedding_model、status | 角色私有记忆；带来源与有效期 |
| `world_fact` | id、subject、predicate、object、truth、visibility、known_by_json、reveal_seq、valid_from_seq、valid_to_seq、source | 客观事实；`reveal_seq` 控制旁白能说到哪 |
| `character_belief` | id、character_id、fact_id、belief_text、confidence、learned_seq、source | 角色以为什么；可错、可矛盾 |
| `relationship_edge` | id、from_id、to_id、axis、value、since_seq、source | 信任/亲密/张力；有向边 |
| `approval_report` | id、chapter_id、revision_id、verdict、blocking_json、suggestions_json、dimensions_json | 审批报告 |
| `gate_record` | id、gate_id、entity_type、entity_id、decision、actor、payload_json、created_at | 闸门审计；G0–G7 每次决策可追溯 |
| `job` | id、type、status、expected_revision、epoch、idempotency_key、payload_json | 生成/固化/导出任务；幂等与恢复 |
| `tool_call` | id、job_id、turn_id、tool、tool_version、actor_id、scope_json、args_hash、result_ids_json、status、error_code、latency_ms、degraded | 工具调用审计；`scope_json` 只存 ID 与 `as_of`；不存 `args` 原文，只存 hash；与 `trace_ref` 互为索引 |

**世界状态不是一张表**，而是 `world_fact` + `character_belief` + `relationship_edge` 在某个 `as_of` 上的投影视图。不要建一张可变的 `world_state` 大表：它会把「当前」焊死，回退和按章审稿都做不了。

**`model_binding` 的生效边界**：每个生成任务在开始时快照绑定；生成中改设置不影响当前任务；改绑定只影响下一拍。继承顺序：`character:<id>` → `character` → `project.default_preset`；其他 agent → `project.default_preset`。

### 7.2 关键字段说明

**`chapter.covered_until_seq`**

审批第 3 章时，不能拿「当前认知」去判，否则第 20 章才揭晓的事会被判成第 3 章越界（假阳性）；重读旧稿又会漏判。做法：章节记录「本稿覆盖到哪个叙事序」，认知视图按 `learned_seq <= covered_until_seq` 展开，查询时按章过滤。

**`beat` 的三段式**

`body` 是正文；`grounding_json` 是依据 ID 列表；`trace_ref` 指向归档的思考/工具调用。只有 `body` 参与后续上下文拼装。`supersedes_id` 加部分唯一索引（一条旧拍只能被替换一次），否则追溯链分叉，UI 判断不出哪个是现行版本。

**`tool_call` 的 `args_hash`**

工具调用只存参数 hash 与结果 ID，不存参数原文。查询词、目标角色、过滤条件都可能泄漏意图；需要复现时用 `job_id + turn_id + tool + scope_json + args_hash` 对齐 `trace_ref`，而不是把原文写进审计表。

**`memory_entry` 的身份**

身份是 `(character_id, kind, text, learned_seq, source_revision)`，不是内容哈希。同一句话在不同章节说两次可以是两条记忆；内容去重是抽取管线的职责，不是数据库唯一索引的职责。

**`world_fact` 与 `character_belief` 分离**

一句台词可能是谎言。角色说「账本在祠堂」只能写进该角色的 belief，不能覆盖客观事实。客观事实由事件、作者确认或记忆管理提案（G7）写入。

### 7.3 六条结构约束

| 约束 | 规则 | 防什么 |
|---|---|---|
| 章↔场景 | `UNIQUE(chapter_id, ord)` | 一章多场景排序错乱；写的时候不知道演哪拍 |
| 单值槽位 | `UNIQUE(scope, slot_key) WHERE valid_to_seq IS NULL` | 同一角色同时「住在上海」和「住在北京」 |
| 时间轴 | 同一 `timeline` 内 `story_start` 随 `idx` 单调不减 | 闪回被误判为时间线错误；插叙打乱因果 |
| 事实有效期 | 物品持有、生死、契约用事实自身的 `valid_from/to` 判，不用叙事序判 | 插叙一段就把已送达的信判成未送达 |
| 认知快照 | 按 `covered_until_seq` 展开，按章过滤 | 用当前认知审早期章节，假阳性/漏判 |
| 内容绑定 | 同一 ID 不能换文本；修改产生新版本 + `supersedes`；一条旧拍只能被替换一次 | 既有认知记录悄悄授权了新秘密；追溯链分叉 |

### 7.4 存储布局与单一真相

```
<project>/
├─ noryth.db            # SQLite（WAL）：状态权威、revision、job、审计
├─ manuscript/          # Markdown 受控镜像：一章一个文件
├─ assets/              # 角色卡、世界观资料、只读参考稿
├─ exports/             # 导出快照
└─ backups/             # 项目级备份与检查点
```

- SQLite 是权威；Markdown 是给人看、给 Git 管的镜像，不是第二真相。
- 向量检索能力 P0 就必须有（角色记忆是核心功能）；独立向量数据库不是 P0 的必需项。P0 把索引放在同一 SQLite 文件（`sqlite-vec` 或 BLOB + 进程内余弦），避免「数据库 + 向量库」双写不一致。
- 规模阈值实测后再决定是否引入独立向量库；`ann_threshold` 写成参数，不提前上 ANN。
- 备份 = 复制项目文件夹；恢复 = 打开备份 + 校验 `schema_version`。

### 7.5 向量与记忆

- **逻辑上每个角色一个 collection**，物理上可以是同表分区 + 强制 `character_id` 过滤；隔离由 `MemoryStore` 接口强制，不靠模型传参。
- **嵌入模型版本化**：`embedding_model` 写进项目元数据；换模型必须全量重建，禁止混维度查询。默认使用应用内置的中文嵌入模型（如 bge-small-zh 级别，CPU 推理，随应用分发），不暴露给用户配置；生成模型全部走云端 API。
- **检索档位**：主角 top_k 8、配角 5、群众 2，可按项目调；重要度与 pin 不进相关性排序，单独成段注入。
- **不做时间衰减**：伏笔、仇恨、承诺、身份不能因为「时间久」被忘掉。记忆退出召回靠「被回收/被 supersede/作者归档」，不靠半衰期。
- **写入侧**：定稿后抽取；否定词与极性先于去重判断（「不喜欢摄影」不是「喜欢摄影」的重复）；单值谓语换宾语走 supersede，多值谓语换宾语可并存。

## 8. 检索与上下文

### 8.1 四层上下文

| 层 | 内容 | 谁可见 | 预算策略 |
|---|---|---|---|
| L0 章级 | 章纲、本章核心事件、目标、禁揭清单 | 编排、审批（全文）；角色、旁白只拿脱敏后的一句话目标，旁白另加场景序列（不含禁揭清单） | 稳定前缀，优先保留 |
| L1 场景级 | 地点、在场者、场景目标、入口/出口条件、上一场结果 | 编排、角色、旁白、审批 | 场景内稳定，优先保留 |
| L2 发言者 | 完整角色卡、限知世界状态、私有记忆检索、最近 N 拍正文、本拍意图 | 仅当前发言者 | 最大块；超预算先压缩历史 |
| L3 旁观者 | 80–150 token 状态卡：位置/情绪/已知/未知/关系张力 | 在场非发言者 | 每人一张；超过 8 人先拆场景 |

- 非发言角色不给完整设定与私有记忆；离场角色完全移出上下文。
- 出场角色超过阈值（默认 8，可配）时，给作者三个选项：拆场景 / 合并工具人 / 启用最小上下文；不静默把所有人塞进去。
- 每轮记录上下文清单（区块 + token），否则成本无法归因。

### 8.2 四种知识，四种读者

| 知识层 | 内容 | 谁能读 | 谁写 |
|---|---|---|---|
| 客观真相 | 作者设定的事实、已发生事件 | 作者、审批（审计）、记忆管理、编排（规划用） | 记忆管理（G7）、作者 |
| 角色信念 | 角色以为的事实，可错、可矛盾 | 该角色、审批、记忆管理（维护）、编排（排戏用） | 记忆管理（从定稿抽取） |
| 读者已知 | 已通过正文揭示给读者的信息 | 旁白、编排 | 系统按 `reveal_seq` 投影 |
| 公开设定 | 世界观常识、地理、历史、组织 | 所有 Agent | 规划（建议）+ 记忆管理（建库/写） |

旁白可以读「结构」（本章场景目标、拍序），但不能读「未揭示的谜底」。旁白的事实来源是「读者已知投影」，不是客观真相全量。这是「旁白不等于上帝」的落地方式。

旁白的「心理旁白」只写可观察的外显与自由间接引语（「她像是想起了什么」），不写未说出口的具体秘密；需要具体内心独白时，把这一拍分配给该角色 Agent，由角色自己写。这样既保留心理描写的质感，又不让旁白获得全知权限。

审批能读私有记忆做审计，但报告里引用记忆 ID 与最小必要证据，不整段复制私有原文；否则报告本身会成为新的泄漏面。

### 8.3 检索管线

- **角色私有记忆**：向量 + 关键词 + 结构化事实三通道；`character_id` 由调用方注入；先过滤可见性，再召回、重排、摘要。中文关键词用 bigram 展开，不依赖分词器；否则整段中文会变成一个 token，查「花生」返回 0 行。
- **公共设定**：向量 + 关键词；不返回任何私有记忆 ID。
- **世界状态**：结构化查询，不走向量；按 `as_of`（章节/叙事序）返回投影。
- **收口**：先绝对下限（头名低于阈值就返回空，注入「无相关记忆」，不把低分包成「我记得」），再相对截断，最后去冗余。**不按本次查询最高分归一化**，否则绝对阈值永远不触发。阈值按嵌入模型校准，不写死一个跨模型通用的数。
- **降级阶梯**：`full → summary → facts only → empty`；降级级别写进日志与 `meta.degraded`，否则「这轮为什么答得差」无法归因。

### 8.4 为什么角色记忆不做时间衰减

角色记忆不是聊天机器人的「用户偏好」，它承担的是长篇因果：

- 第 3 章埋的伏笔，第 40 章才回收；半衰期等于保证它在回收前先被忘掉。
- 一次背叛、一个承诺、一条身份秘密，不能因为「过去很久」而降低权重。
- 事实的失效只由 `valid_to_seq`（故事内有效期）决定，不由真实时间决定。

排序用「相关性 + 重要度 + 故事内近因 + pin」；pin 的含义是「不衰减、不归档」，不是「更相关」，所以单独成段注入，不混进相关性排序。

## 9. 非功能设计

### 9.1 Electron 进程与安全

- **main process**：Agent 运行时、SQLite、向量索引、文件 IO、模型调用。**renderer**：只做 UI，不持有 API Key。
- **Windows 10/11 x64 首发**：原生模块（better-sqlite3 / sqlite-vec）按 Windows 预编译并做 Electron ABI 重建；NSIS 安装包 + 自动更新（从 GitHub Releases 拉取），更新包做签名校验，更新检查失败不阻塞启动；业务层不写 Windows 特有逻辑，保留未来移植空间。
- `contextIsolation: true`、`nodeIntegration: false`、IPC 白名单 + 参数校验；renderer 不能任意读文件。
- API Key 用 Electron `safeStorage` 加密后存本地（Windows DPAPI）；按预设分别保存，不进 localStorage、不进日志。
- CSP 限制外链；禁用 `remote` 模块；导出走主进程对话框；不支持导入现有小说/大纲。

### 9.2 性能目标（待 M0 实测校准）

| 项 | 目标 | 口径 |
|---|---|---|
| 流式首字 | 尽快出现；具体 P95 由供应商与网络决定 | 从点击生成到首个 token |
| 单拍完成 | 与正文长度、检索条数相关；M0 记录 P50/P95 | 不含作者确认时间 |
| 进程内检索 | 2 万条记忆的进程内检索应保持交互级 | 单次 top_k 查询 |
| 章节切换 | 交互级，不卡 UI | 从点击到正文可读 |
| 崩溃恢复 | 已提交拍零丢失；生成中的拍可重试 | 强杀进程后重启 |

不在这里写精确毫秒数：同一套代码在 Python/Node/Electron 打包环境下的差异可达一个数量级，M0 用产品运行时实测后再回填。

### 9.3 模型接入、路由与成本

- **统一适配器**：所有云端供应商都走 OpenAI-compatible 的 chat completions 协议；预设负责 base URL 与路径；嵌入默认使用应用内置模型，不走供应商。适配器负责能力探测（流式、工具调用、JSON mode、上下文长度）与错误归一化。
- **工具调用能力**：探测不到 tool calling 的模型不进入默认路由；已绑定的按 §4.9.2 走 JSON 回退，连续 2 次协议失败标 `tool_protocol_error`，不静默裸答。
- **内置预设**：OpenAI / DeepSeek / 通义（可扩展）。每个预设预填 base URL、模型清单、上下文长度与计价；作者只需填 API Key，首次启动选择预设，之后可随时切换。
- **逐 Agent 绑定**：设置中按 Agent 绑定 provider + model；角色可展开到每个角色实例；未绑定按「角色实例 → 角色 → 项目默认」继承，其他 Agent 直接继承项目默认。绑定在每拍开始时快照，生成中不改。
- **默认路由（作者未绑定时的回退）**：角色/旁白优先强模型；规划/编排用强推理；审批尽量用与生成不同的供应商；记忆抽取用便宜模型 + schema 校验。作者在设置中的逐 Agent 绑定优先于默认路由。
- **降级**：供应商限流/超时 → 重试 2 次 → 提示切换预设或暂停；不静默降级到弱模型，不把供应商差异泄漏到业务逻辑。
- **按章预算**：自动模式开跑前给预估区间；按 token 计费；超预算或超时暂停，不静默烧钱。
- **前缀缓存**：角色卡、系统提示词、章级上下文保持稳定前缀，动态内容放后面；供应商支持前缀缓存时启用。
- **轨迹与工具结果不回流**：`trace` 与上一拍的工具结果都不进下一轮，下一拍要查再调工具；避免成本随拍数复利增长，也避免旧引用被当成新依据。
- **上下文预算**：L2 最大，但先压缩历史拍，再降 top_k，最后裁旁观者；不裁角色卡核心字段。

### 9.4 幂等、并发与恢复

- 每个生成/固化/导出任务有 `job_id`、`expected_revision`、`epoch`、`idempotency_key`。
- 同一项目同一时刻只允许一个写任务；跨章可并行读，不可并行写世界状态。
- 迟到结果由提交层拒绝：用户已回退、revision 已变、epoch 已过期，三者任一即丢弃。
- 取消网络请求不保证远端停止；只能保证结果不落盘。
- 启动扫描 `job` 表：`generating`/`applying` 标 `interrupted`，可重试；不自动重放有副作用的任务。

### 9.5 可观测与审计

- 每拍记录：上下文区块、token、检索命中 ID、降级级别、provider（预设）、模型、agent_key、binding_version、endpoint（脱敏）、耗时、费用。
- 每次闸门记录：谁、何时、通过了什么、拒绝了什么。
- 每次写入记录：revision、hash、patch、来源 Agent。
- 每次工具调用记录：`tool`、`version`、`actor_id`、`args_hash`、`result_ids`、耗时、`degraded`、`error_code`（§4.9.7）。
- 错误分类：`model_error`、`memory_empty`、`context_trimmed`、`storyboard_conflict`、`character_refusal`、`storyboard_exhausted`、`file_conflict`、`human_takeover`、`tool_unavailable`、`tool_protocol_error`、`tool_budget_exceeded`。

### 9.6 数据导出与删除

- 项目可整体导出/删除；删除是删项目文件夹 + 清空缓存，不做「假删除」。

## 11. 指标

**北极星**：每周作者点击「定稿」的章节字数（不是生成字数，也不是 token 消耗）。

| 层 | 指标 | 定义 | 口径 |
|---|---|---|---|
| 质量 | 审批一次通过率 | 无阻断问题的章节 / 审批章节 | 按章 |
| 质量 | 拍采纳率 | 确认拍 / 生成拍 | 重生成算多次生成 |
| 质量 | 越界泄漏 | 进入提示词的未授权事实条数 / 装配次数 | 硬门 = 0；另做人工抽检，不混模型说漏嘴率 |
| 质量 | 工具越权成功调用 | 未授权工具成功执行的次数 | 硬门 = 0；与 §4.9.7 同口径 |
| 质量 | 记忆错误率 | 作者删除/修改的固化条目 / 提案条目 | 按次 |
| 质量 | 声音区分度 | 句长分布 √JSD + 口头禅/第一人称/问句率差异，合成 0–1 | 每场关账后对在场角色两两算；参考阈值 0.18，需用中文语料重标 |
| 质量 | 伏笔回收率 | 已回收伏笔 / 已埋伏笔 | 按卷；超期只报节奏问题，不报逻辑错误 |
| 效率 | 每千字作者净操作时间 | 点击/输入/切页耗时，不含阅读 | 客户端埋点 |
| 效率 | 每拍确认耗时 | 从拍卡出现到作者确认的时长 | 默认逐拍的核心体验指标；按拍统计 |
| 效率 | 从立项到第一章定稿 | 自然日 | 新手引导后测 |
| 成本 | 每万字定稿成本 | 云端 token 费用 + 存储 | 按项目 |
| 成本 | 每 Agent 成本占比 | 按 agent_key 汇总 token 费用 / 本章总费用 | 用于发现某个 Agent 吃预算 |
| 信任 | 回退成功率 | 回退后逐域状态一致的次数 / 回退次数 | 消息、事实、认知、关系、正文、记忆逐域校验 |

两个口径必须分开写：

- **过滤器指标**：未授权事实进入提示词的条数。它衡量上下文防火墙，能归因到装配代码。
- **生成指标**：模型说漏嘴率。它混入模型行为，不能用来判断过滤器是否失效。

把两者合成一个「泄漏率」，既无法定位，也会让过滤器永远看起来「差不多」。

## 12. 风险

| 风险 | 表现 | 机制 | 对策 | 退出标准 |
|---|---|---|---|---|
| 自评偏置 | 审批对自家生成的内容偏宽松 | 生成与审批同模型、同提示词 | 异构模型复检；阻断项必须给证据；作者抽检 | 抽检 30 章，阻断项漏报可统计 |
| 记忆污染 | 错误抽取进入长期记忆，后续章节跟着错 | 直接追加、无来源、无重建 | 提案制 + `source_revision` + 可重建 + 作者删除 | 任一错误记忆可在 3 步内定位并失效 |
| 角色同质化 | 所有角色说话像同一个人 | 角色卡 voice 字段太弱；上下文互相污染 | voice 字段必填；句长/口头禅指标；盲测 | 同场两角色区分度低于阈值时报警 |
| 模型拼盘风格漂移 | 同一场不同角色文风差异明显 | 不同 Agent 绑不同模型；温度/提示差异 | 默认同一预设；角色覆盖是显式操作；声音区分度监控 | 同场声音区分度低于阈值时提示换回统一模型 |
| 成本失控 | 自动模式长跑，云端账单或耗时不可控 | 无预算、无拍数上限、轨迹与工具结果回流 | 章预算 + max_beats + 轨迹/工具结果不回流 + 便宜模型抽取 | 超预算必暂停，账单可归因到章 |
| 无法收束 | 场景永远演不完，或硬截断 | 出口条件是自然语言，模型自评 | 机器可判定 exit DSL + max_beats + 耗尽告警 | 每场都有明确 closed 或 WARN |
| 双真相 | DB 与 Markdown 不一致 | 外部编辑、双写失败、无 hash 校验 | DB 权威 + 受控镜像 + hash 冲突检测 + outbox 重试 | 冲突必拦截，不静默覆盖 |
| 限知泄漏 | 角色知道不该知道的事 | 检索过滤写错、模型传参、上下文混装 | 接口强制 scope + 审计 + 单元测试 | 未授权事实进入提示词 = 0 |
| 工具越权 / 契约漂移 | 未授权工具被下发；身份由模型传参；文档与代码授权不一致 | 白名单靠提示词、schema 含身份字段、双份清单 | 单一注册表 + 运行时注入 + CI 比对 + 越权契约测试 | 未授权工具成功调用 = 0；CI 不一致即阻断 |
| 长篇漂移 | 第 30 章忘了第 3 章的设定 | 只靠最近上下文 | L0/L1 稳定层 + 章末摘要 + 关键事实常驻 | 每章开演前有「本章必须记住的 5 件事」 |
| 供应商限流/不可用 | 生成中断、成本飙升或无法继续 | 单一供应商故障、限流、涨价 | 预设切换 + 重试 2 次 + 暂停；不静默降级；用量告警 | 任一预设故障可在 1 次切换内继续；不丢已确认拍 |
| 逐拍操作疲劳 | 每拍确认太频繁，作者改用自动或放弃 | 默认逐拍但确认成本高；快捷键/预览不足 | 一键确认/重生成/编辑；每拍字数上限；自动模式显式切换 | 每拍确认中位耗时在可接受范围（M0 实测后定） |
| Windows 单平台债 | 未来移植成本高 | 业务层写死路径/权限/进程行为 | 平台抽象层；业务层不写 Windows 特有逻辑 | 新增平台只改适配层，不改业务模块 |
| 自动更新不可达 | GitHub Releases 在部分网络环境下载失败 | 网络限制、代理、证书 | 更新检查失败不阻塞启动；提供手动下载安装包；失败重试 | 更新失败不影响打开项目与写作 |
| 冷启动门槛高 | 不能导入旧稿，作者不愿从零建蓝图 | 无导入 + 蓝图工作量大 | 蓝图向导（P1）；旧稿只做只读附件；M0 先做「1 小时审完」的蓝图流程 | 新用户从立项到 G1 的时长达标（M0 实测） |

## 附录 D：术语与文件对照

| 概念 | 存储位置 | 写入者 | 备注 |
|---|---|---|---|
| 蓝图/章纲 | `outline_node` | 规划（提交）、作者（批准） | 改版触发影响分析 |
| 角色卡 | `character.card_json` | 规划（提交）、作者（批准） | 版本化，不换 ID |
| 分镜 | `scene` + `beat`（planned） | 编排（提交） | 开演前可改 |
| 初稿 | `beat.body` + `revision(kind=draft)` | 文档控制器 | 审批 patch 也只写这里 |
| 定稿 | `revision(kind=final)` | 文档控制器，作者触发 | 只读快照 |
| 私有记忆 | `memory_entry` + 向量索引 | 记忆管理（G7 后） | 按 `character_id` 隔离 |

| 审批报告 | `approval_report` | 审批 | 只读交付，不自动改稿 |
| 审计 | `job` + `gate_record` + 日志 | 系统 | 每次写入可追溯 |
| 工具调用 | `tool_call` + `trace_ref` 归档 | 运行时 | 参数只存 hash；结果引用可回放 |
| 工具清单 | `docs/tools/*.json`（M0 生成）+ §4.10 | 工具层维护 | 契约变更走版本与 CI 比对 |
