# ADR-0008 多供应商路由与故障切换

- 状态：**已决定**（2026-11-21）
- 对应：PHASE-21 M2-4、PRD §5.6 / §9.3、DEV-PLAN §7.7
- 关联：ADR-0003（供应商预设）、ADR-0009（异构默认值）

## 背景

M0–M1 的失败策略是「重试 2 次，然后暂停或提示切换预设」。作者在设置里换一家需要手动操作，主家故障时没有可审计的「用了备用」记录；审批异构与可用性之间也没有优先级规则。M2-4 要求显式的多供应商路由，但明确不做自动降级、不做负载均衡、不按价格选家。

## 选项

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 静默降级到备用/弱模型 | 主家失败自动换一家，不告诉作者 | 拒绝：掩盖故障，账单与归因不可解释 |
| B. 作者显式配置备用家 + 可见切换 | 总开关、触发条件、冷却、逐 Agent 备用；状态栏徽标 + `turn_metric` 留痕 | **采用** |
| C. 跨供应商负载均衡 / 按价格选家 | 按成本或延迟自动分配 | 拒绝：超出单人作者范围，破坏「绑定可解释」 |
| D. 真实供应商健康检查端点 | 主动探测每家可用性 | 暂不做：没有统一端点，探测成本与误判都比错误驱动高 |

## 决定

1. **设置形状**：`routing = { enabled, fallbackOn, cooldownMs, agents }`，默认关闭；旧 `settings.json` 缺字段时按默认值读取，不报错。
2. **触发分类**：只认适配器归一化后的错误——`rate_limit`、`server`（5xx `model_error`）、`timeout` 可切换；`auth`、`content_filter`、`protocol`、`context_overflow`、`stale_revision` 永不切换；作者取消（aborted）不计入健康。
3. **切换时机**：只在回合开始前。job 创建时的绑定快照保留主家；本次实际绑定由路由决定，`turn_metric` 逐拍记录实际 provider/model；失败的那一拍不落盘，按下暂停处理；下一拍或下一 job 才用备用。同一拍中途不换模型。
4. **健康与熔断（内存）**：一次可重试失败 → 冷却 `cooldownMs`（默认 60s），期间优先备用；同家 5 分钟内累计 3 次 → 熔断打开同样时长；冷却后允许一次半开探测，成功清零、失败重开。状态只在内存，重启清空并记录一次 `health_reset`；宁可多试一次，也不把一家永久拉黑。
5. **主备都不可用**：抛 `routing_exhausted`，不在同一拍里反复重试；已确认拍不受影响。
6. **备用家资格**：预设已启用、已通过测试连接、有 Key（或 E2E 假模型）、模型已知且具备工具能力、与主家不是同一家。资格在每次解析时重新校验，设置页可保存未通过测试的条目但运行时不会使用。
7. **审批优先级**：先异构、后健康检查；异构选中的第二家不健康时，备用家不得等于生成家，否则保持 `hetero_unavailable`（详见 ADR-0009 与 PHASE-21 §5.3）。
8. **留痕与审计**：切换写 `turn_metric.context_json.routing={from,to,reason,error,at}` 与日志 `routing_fallback`；不改 `model_binding_audit`（只记录作者改绑定）、不改 `gate_record`、不改 `approval_report` 的判定（只改 provider/model 归因）。
9. **覆盖范围**：规划、编排、角色、旁白、审批、记忆六个 Agent 都走同一个 `RoutingRuntime`；角色实例归一到 `character` 配置行。假适配器模式不参与路由，避免归因分叉。

## 后果

- 作者能看到「正在用备用」与原因，但必须自己配置备用家；没有配置时行为与阶段 20 完全一致。
- 重启后健康清零，可能多打一次失败的主家；这是刻意的可用性取舍。
- 一次失败就切换意味着短时抖动会多用备用家 60 秒；状态栏徽标与报表 provider 列让这一点可见，不静默。
- 路由不改变预算与成本口径：`turn_metric.cost_cny` 按实际 provider 的预设计价计算；未计价的家仍显示「费用为下限」。

## 回退

- 关闭 `routing.enabled` 即回到阶段 20 的行为；不迁移数据、不重建索引。
- 删除 `routing` 字段的旧设置文件仍可读（Zod 默认值）。
- 若健康状态误判，重启进程或等待冷却即可；不提供「永久拉黑」开关。
