# 04 · 界面与交互

---

## 1. 信息架构

```
首页（项目选择器）
 └─ 新建项目向导（选文件夹 → 名称 → 题材 → 模型预设 → 完成）
      └─ 工作台（四区）
           ├─ 剧场（自动/单步/用户扮演）
           ├─ 正文（章节编辑）
           ├─ 时间轴（检查点 / 分支 / Git）
           └─ 设定（角色 / 世界 / 事件卡 / 谓词）
设置（全局，不随项目变）
```

三个页面之间是**整页切换**，不是抽屉。理由：创作时需要"我在哪"的空间感；抽屉会让用户误以为设定页和正文页是同一个上下文。


新建向导五步，每步一屏，可后退：

| 步 | 内容 | 校验 |
|---|---|---|
| 1 | 选择文件夹 | 必须是空目录，或含 `noryth.json` 的已有项目；不能是项目内部子目录 |
| 2 | 项目名 + 题材 + 篇幅目标 | 名字非空；篇幅用于估算章节数 |
| 3 | 模型预设 | 主持人（贵）/ 角色（中）/ 摘要与调度（便宜）三档，可分别指定 |
| 4 | 初始设定 | 三选一：从零开始 / 导入 Markdown 设定 / 用规划 Agent 生成 |
| 5 | 确认 | 展示将创建的文件清单 |

**第 5 步必须列出文件清单**，因为用户是在自己的文件夹里操作，看不见会发生什么就会犹豫。清单固定 7 项（代码里的唯一权威是 `INIT_ENTRY_SPECS`）：

| # | 路径 | 类型 | 用途 |
|---|---|---|---|
| 1 | `noryth.json` | 文件 | 项目清单：id / 名称 / schema 版本 / 分支指针 / 设置差异 |
| 2 | `.noryth/` | 目录 | 项目状态目录：数据库、日志、发布状态 |
| 3 | `.noryth/project.db` | 文件 | SQLite 权威库；Markdown 只是受控镜像 |
| 4 | `chapters/` | 目录 | 正文章节，一章一个 Markdown 文件 |
| 5 | `skills/` | 目录 | 项目级 skill，与全局同名时项目级覆盖（§9.3） |
| 6 | `.gitignore` | 文件 | 排除运行时数据库与日志，避免二进制进 Git |
| 7 | `.git/` | 目录 | 本地版本库；首次提交携带 `Noryth-Checkpoint` |

## 3. 工作台布局

### 3.1 尺寸与折叠

```
┌──┬──────────────┬──────────────────────┬────────────┬──────────┐
│  │              │                      │            │          │
│导│  场景/会话    │   剧场（对话流）       │  正文预览   │ 文件/检视 │
│航│              │                      │            │          │
│56│  200–360     │        flex          │  320–480   │ 220–320  │
│  │              │                      │            │          │
└──┴──────────────┴──────────────────────┴────────────┴──────────┘
   └ 可折叠          └ 折叠后吃满           └ 可关闭      └ 可折叠
```

- **1440 px（四区）**：`56 + 252 + 832 + 300 = 1440`。此时正文预览不占列，用 `Ctrl+2` 在「剧场 / 正文」之间切换。
- **1600 px（分屏，推荐）**：`56 + 252 + 644 + 400 + 248 = 1600`。剧场与正文同时可见——这是写作者的默认姿势：一边演，一边看它变成稿子。
- 左栏、预览栏、右栏均可拖拽、可折叠（`Ctrl+1/2/3`）。折叠任一栏，主区吃满剩余宽度。
- **窄屏（< 1200）**：预览栏与右栏改为抽屉（浮层），不挤压对话区。
- **更宽（≥ 1800）**：预览栏可再开「修订对比」，左右分屏看 diff。

### 3.2 四种预设

| 预设 | 左栏 | 主区 | 第三栏 | 右栏 | 用于 |
|---|---|---|---|---|---|
| **分屏写作**（默认） | 场景 + Agent + 章节 | 剧场（气泡） | 正文预览 | 文件 / 检视 | 边演边写 |
| **剧场** | 场景 + Agent | 剧场（更宽） | — | 检视器 | 专注推进 |
| **写作** | 章节树 | 正文编辑器 | 章节大纲 | 检视器 | 润色定稿 |
| **审阅** | issue 列表 | 正文 + 行内批注 | diff / 证据 | 证据链 | 审批修订 |

预设只是栏宽 + 主区组件的组合，用户可以自己调完再存成「我的布局」。

### 3.3 左栏：场景与 Agent

```
┌─────────────────────────┐
│ [场景] [Agent]  [+ 新建] │
├─────────────────────────┤
│ 卷一 · 雨夜              │
│ ● s17 雨夜·账本   进行中  │
│   第 12/40 拍            │
│ ○ s16 客栈·试探   已关闭  │

│  旁白       5 拍  ▮▮    │
│  ── 不在场 ──            │

```

两个细节：
- **不在场的 Agent 显示为灰色且不可点发言**。这比"点了之后报错"省一次挫败。
- 每个 Agent 后面显示已发言拍数。用户能一眼看出谁被冷落了——这比任何"平衡性指标"都直观。

## 4. 对话区（剧场主区）

### 4.1 三种消息形态

对话区是**聊天式气泡**，不是卡片列表。三种形态对应三种"谁在说话"：

```
  旁白（整幅段落，不是气泡——它没有说话人）
┌────────────────────────────────────────────────────────┐
│ 客栈的灯点到二更，油快尽了。林砚把账本压在肘下……            │
└────────────────────────────────────────────────────────┘

  ────────── 导演  抽牌「不速之客」· 冲突 1.7 → 2.1 ──────────

  ┌──┐  ┌──────────────────────────────────────────────┐
  │沈│  │ 沈昼  角色                          第 9 拍    │
  └──┘  │ 「你母亲的忌日，快到了吧。」                      │
        │ 他把伞收拢，水顺着伞骨一滴滴落在门槛上。            │
        │ ┃ 心理 · 仅读者可见                              │
        │ ┃ 他在试探我。可他怎么知道是这几天？                │
        │ [意图：逼林砚先开口] [⚠ 知识越界·已拦截并重写]      │
        │                     为什么是沈昼？ 重写 回退        │
        └──────────────────────────────────────────────┘
```

六个必须存在的元素：

1. **头像 + 名字 + 拍号**。一眼分清"谁在说"和"第几拍"。头像用角色色，与左栏 Agent 的色点一致，跨面板对得上。
2. **旁白不是气泡**。它没有头像、没有圆角背景，只有一条左侧竖线与衬线体——读者立刻知道这是"叙述"而不是"某人说的话"。
3. **心理单独一块且标注「仅读者可见」**。默认展开给作者看，但明确写出这条**不进其他角色上下文**——这是知识边界在 UI 上的可视化，不是装饰。
4. **越界警告贴在气泡里**。不是弹窗、不是日志。拦截了显示红色，放行了显示黄色，点开能看到"它不知道哪一条"。
5. **意图徽章**。作者要知道这一拍角色想干什么，否则无法判断"没推进"是角色的错还是调度的错。
6. **三个行内动作**：为什么是它 / 重写 / 回退。覆盖 90% 的干预需求。

「重写」点下去**不是立刻重跑**，而是先弹三个选项（默认第一个）：

```
重写这一拍？
  ● 从这一拍开新分支重演（旧分支保留）        ← 默认
  ○ 只替换这一拍，后面 5 拍标记为"基于旧文本"
  ○ 替换并重新生成后面 5 拍
```

默认"开分支"的理由：原地替换会让后面五拍在回应一句已经不存在的话，而界面上看不出任何异常。用户只会觉得"人物怎么忽然答非所问"，然后开始怀疑模型。

导演事件用居中分隔线，而不是气泡——它是**系统动作**，不是谁说的话。这一条区分很重要：用户改稿时最容易把"导演发牌"误读成"旁白在叙述"。

"为什么是它"展开的是 `beat.breakdown`：

```
goal_rel 1.0 × 0.34 = 0.340   ← 本场目标：夺回账本
addressed 1.0 × 0.30 = 0.300  ← 上一拍林砚点了他的名
stake    0.57 × 0.16 = 0.090  ← 0.15 + 0.22×(2.1/4) + 0.30（秘密受威胁）
narrator  0    × 0.12 = 0
initiative 0.6 × 0.08 = 0.048
jitter  = 0.021
─────────────────────────
base 0.778 + 抖动 0.021 = 0.799   阻尼后 0.799（被点名豁免）   硬上限未触发
```

这一段是"可解释性"的全部。没有它，用户会觉得系统在乱点人。

### 4.2 顶部控制条

控制条只有一行，放在对话区顶部（不是底部）。理由：底部要留给输入框。

```
剧场   [自动][单步][指定][收束]      视点 林砚   退出条件 ○未满足   冲突 ▮▮▮▯▯ 2.1   12/40 拍
```

- **自动**：连续跑，每拍后短暂停顿（可配 0–3 秒），让用户跟得上。
- **单步**：跑一拍停一拍。**默认就是单步**——自动跑太快，用户来不及反应，而"跟不上"是弃用的第一原因。
- **指定**：下拉选人，强制下一拍由它说（`beat.mode='user_pick'`），同时豁免阻尼与硬上限。
- **收束**：手动进 `closing`，让旁白写收尾。
- 冲突条 5 格对应 0–4 级；退出条件悬停展开表达式，点击跳到场景卡。

### 4.3 常驻输入框

输入框**一直在**，不是"轮到你才出现"：

```
┌──────────────────────────────────────────────────────────┐
│ 以 林砚 的身份插话                    第 11 拍 · 下一位：旁白 │
│ 写台词，或只写一个动作……                                   │
│ [发送 ⏎] [让 AI 代写这一拍] [跳过]     Shift+Enter 换行 ⌃⏎ 强制发送 │
└──────────────────────────────────────────────────────────┘
```

三个设计决定：

1. **常驻而不是轮询**。用户可以随时插一句（包括"以旁白身份补一句环境"）。剧场感来自"你随时能上台"，而不是"等系统叫号"。系统仍然按调度器决定**下一拍**是谁，用户插话会作为一条 `user` 消息插入并影响后续 `addressed`。
2. **轮到你时才有强提示**：输入框左边框变金色，顶部显示「轮到你了 · 第 N 拍」。其余时候它安静地待着。
3. **「让 AI 代写这一拍」保留席位**。用户扮演不等于每拍都要手写；写不动时一键交回 AI，席位不丢，下一拍还能自己接。

`发送` 与 `Ctrl+Enter` 的区分见 §12：中文输入法组合态下按 `Enter` 是选词，不能当成发送。

**旁白席位可被用户接管**——需求里明确要求了。接管后旁白提示词仍然生效（防止用户自己越界），只是生成者换成用户。

## 5. 正文预览栏（第三栏）

```
02 账本.md  修订 r3                        联动本场  ⋯
──────────────────────────────────────────────────────
第二章　账本
1,284 字 · 由第 9–12 拍生成 · 待审

　　客栈的灯点到二更，油快尽了。林砚把账本压在肘下，一页一页翻得很慢。
　　「你母亲的忌日，快到了吧。」
▏林砚没有抬头。他的手指在账本边缘停了一下，又若无其事地翻过一页。   新增
　　沈昼没有答。他把伞靠在门边，水顺着伞骨一滴滴落在门槛上。
──────────────────────────────────────────────────────
第 5 段 · 与第 12 拍同步                ⌘⇧D 比对修订   送审
```

四条规则：

1. **只读预览，双击才进编辑器**。预览不抢焦点——它的职责是"看着稿子长出来"，不是"改它"。
2. **新增段落带金色左边线与「新增」角标**。作者一眼看出"这一段是刚才那几拍变出来的"，不用回忆。
3. **底部显示「第 N 段 ↔ 第 M 拍」，点击跳回那一拍**。这是双向的：从剧场能看正文，从正文能回到演出。没有这条，正文和剧场就是两个割裂的软件。
4. **「联动本场」是开关**。关掉后预览不再跟随当前场景滚动，适合回头改旧章；开着时它自动滚到正在生成的那一段。

为什么它必须与对话区同时可见：写作 Agent 的产出质量，只有在**一边看演出、一边看稿子**时才判断得出来。来回切标签会让"这句是不是演出来的"变成一个记忆题。

**性能**：预览只渲染可视区（虚拟化），10 万字章节的滚动不能卡。段落级 diff 用 `revision.content` 的 Myers 算法预处理，打开对比时不再重算。

## 7. 回退交互（时间轴）

回退是**最容易做错**的交互。设计目标是：让用户看见"退回去会失去什么"，并且知道"退回去不等于销毁"。

```
┌──────────────────────────────────────────────────────────────┐
│ 时间轴                                     [分支: main ▾]     │
├──────────────────────────────────────────────────────────────┤
│  ● 现在                          第 4127 事件 · 第 12 拍       │
│  │                                                           │
│  ○ 检查点 · 场景 s16 关闭          第 3980 事件               │
│  │   ↳ 影响：消息 34 · 事实 6 · 认知 11 · 关系 3               │
│  │            正文 2 · 卡片 1 · 摘要 2 · 向量 41               │
│  │                                                            │
│  ○ Git · a3f9c2 "第二章初稿"        绑定检查点 3980            │
│  │                                                            │
│  ○ 检查点 · 手动 "试验：让沈昼先动手"  第 3901 事件            │
│  │   ↳ 分支 exp-1 从此处开出（仍可切换回去）                    │
│  │                                                            │
│  ○ 检查点 · 自动                    第 3800 事件               │
└──────────────────────────────────────────────────────────────┘
                            [回退到选中检查点]
```

**回退确认框必须列出 8 个域的计数**（上图的 `↳ 影响` 行）。这不是装饰——它是 I3 不变量在 UI 上的强制表达。用户看到"会失去 34 条消息、11 条认知"，才会理解"回退"不是"删几条聊天记录"。

确认框底部固定一句：

> 回退会创建一个新分支，当前分支保留，随时可以切回。已发送给模型的请求和已产生的费用不会退回。

第二句是诚实。本地回退救不了已经花掉的钱。

## 8. 版本控制（Git）界面

与时间轴同一个页面，切换 tab：

```
[检查点] [Git 提交] [分支]

┌────────────────┬────────────────────────────────────────┐
│ a3f9c2  2 小时前│  chapters/02.md                        │
│ 第二章初稿       │  ─────────────────────────────────────  │
│ b71e04  昨天    │  - 他把账本塞进袖口。                   │
│ 第一章修订       │  + 他把账本塞进袖口，指节泛白。          │
│ c02d11  3 天前  │                                        │
│ 初始化           │  + 雨声忽然大了。                       │
└────────────────┴────────────────────────────────────────┘
```

- Diff 按章节分组，Markdown 行级。
- 每个 commit 显示绑定的检查点（`Noryth-Checkpoint: <id>`），点击可跳到时间轴。
- "从这次提交恢复" → 读 `noryth.json` + `.noryth/state.json.zst` → 开新分支。**不是 `git checkout`**，因为 `git checkout` 只能恢复章节文件，恢复不了角色记忆。

## 9. 设置

| Tab | 内容 |
|---|---|
| 常规 | 语言、自动保存间隔、单步默认停顿、启动时打开上次项目 |
| 外观 | 主题、字号、正文字体、行宽、编辑器主题 |
| 模型 | 三档模型（主持人 / 角色 / 摘要调度）、温度、最大输出、超时、重试、**成本护栏** |
| Agent | 六类 Agent 的默认模型、提示词覆盖、启用开关、权限（审批→修订直连） |
| Skill | 技能列表、启用/停用、打开文件夹、新建（模板） |
| 密钥 | 供应商 key（只存 OS 凭据库，设置里只留引用）、测试连接 |
| 关于 | 版本、schema 版本、数据目录、日志目录、导出诊断包 |

### 9.1 设置项 vs 参数表：两套配置，边界必须清楚

| | 管什么 | 谁改 | 存在哪 | 进 Git |
|---|---|---|---|---|
| **设置** | 应用与项目偏好：主题、模型、密钥引用、开关 | 用户 | `~/.noryth/settings.json`（全局）+ `<项目>/noryth.json`（覆盖） | 项目级进，全局不进 |
| **params.yaml** | 算法超参：权重、阈值、预算 | 开发者 | `docs/params.yaml` → 打包进 `resources/` | 是 |

设置页**不暴露** `params.yaml`。用户想调"故事推进快慢"，该改的是场景目标与事件卡密度，不是 `w.addressed` 的权重——把算法超参摊给用户，等于把调参责任推给不懂它的人。

确实需要开放的少量开关（如"旁白频率"）做成**语义化档位**（少 / 标准 / 多），映射到参数值，不露数字。

### 9.2 设置项 schema

```ts
// 全局 ~/.noryth/settings.json；项目级 noryth.json 只写差异字段
type ModelRef = {
  provider: "openai" | "anthropic" | "ollama" | string;
  model: string;
  keyRef: string;                      // 形如 "os:openai"，永不存明文
};

type Settings = {
  locale: "zh-CN" | "en-US";           // 默认 zh-CN
  theme: "dark" | "light" | "system";  // 默认 dark
  editor: { fontFamily: string; fontSize: number; lineWidth: number };   // 15 / 760
  autosaveMs: number;                  // 默认 2000
  stepPauseMs: number;                 // 默认 0
  openLastProject: boolean;            // 默认 true
  models: { director: ModelRef; character: ModelRef; utility: ModelRef };
  generation: { temperature: number; maxTokens: number; timeoutMs: number; retries: number };
  budget: { perProjectCny: number; warnAt: number; stopAt: number };     // 0.8 / 1.0
  agents: Record<AgentRole, { enabled: boolean; model?: ModelRef; promptOverride?: string }>;
  permissions: { criticToReviser: boolean; autoApplyRevision: boolean }; // 默认都 false
  skills: { enabled: string[]; maxActive: number };                      // 默认 [] / 3
  diagnostic: { includeProse: boolean };                                 // 默认 false
};
```

三条硬规则：

1. **密钥只有引用，没有值**。`keyRef` 指向 OS 凭据库条目；设置文件可以进 Git、可以贴给别人、可以进诊断包。
2. **项目级只写差异**，不复制整份全局。否则改全局对老项目不生效，出现"新项目好了、老项目照旧"的幽灵 bug。
3. **每个键有默认值且可缺省**。文件损坏时应用仍能启动（降级默认 + 一条警告），而不是白屏。

### 9.3 Skill 的运行时机制

Skill 不是插件，是**可复用的提示词片段 + 命中条件**。它不执行代码、不调工具（受 I4 约束），只在特定条件下被拼进某类 Agent 的上下文。

```
skills/<name>/SKILL.md      # 必需：frontmatter(description, when, priority) + 正文 ≤ 800 tok
```

```yaml
---
name: 武侠打斗
description: 写近身搏斗时的节奏与招式描写规范
when:
  scene_kind: [fight]         # 取自场景卡 goal.type / 标签
  roles: [narrator, character]
priority: 10
---
（正文：招式命名风格、节奏要求、禁用词……）
```

注入规则：

- 只在 `when` 命中时加载。命中判定用**场景卡字段**，不做语义匹配——语义匹配会让"这一拍为什么多了这段提示词"无法解释，也无法复现。
- 同时在效 **≤ 3 个**，总预算 **≤ 800 tok**；超出按 `priority` 截断并记 `WARN skill_budget`。
- 注入位置：**角色卡之后、输出契约之前**。这一段在整场戏里逐字节稳定，不会破坏前缀缓存。
- 每次加载把 `skill.name@sha256[:8]` 写进 `beat.breakdown.skills`，复盘能回答"这一拍用的是哪一版"。
- 项目 `skills/` 与全局 `~/.noryth/skills/` 同名时**项目级覆盖**，设置页标出冲突。

**不做**：不做市场、不做远程拉取、**不允许 skill 携带可执行脚本**。前两个会把"提示词片段"变成供应链问题；第三个在"模型无写权限"的架构里是直接破防。将来真要做，必须走显式授权 + 签名。

## 10. CLI 命令面

CLI 不是过渡产物：P0–P3 的全部验收都跑在它上面（见 `05-roadmap.md`）。它必须能**独立完成一次完整创作**，不依赖 GUI。

### 10.1 全局约定

```
noryth <command> [args] [--project <dir>] [--json] [--yes] [--offline] [--verbose]
```

| 约定 | 说明 |
|---|---|
| `--project` | 缺省从当前目录向上查找 `noryth.json` |
| `--json` | 输出单行 JSON 信封，供脚本与 CI 消费 |
| `--yes` | 跳过交互确认（仅 CI 用） |
| `--offline` | 禁止网络；只允许读命令与 stub 生成 |
| 危险命令 | `restore` / `import` / `delete` 必须二次确认，`--yes` 才能跳过 |

### 10.2 命令表

| 命令 | 作用 | 期 |
|---|---|---|
| `init <dir>` | 建项目骨架（7 项文件/目录，清单见 §2 第 5 步） | P0 |
| `open [dir]` | 打开并打印状态摘要 | P0 |
| `status` | 分支 / head_seq / 场景 / 字数 / 未结线索 / 预算 | P0 |
| `doctor` | 环境自检：SQLite 版本、Git、模型连通、目录权限 | P0 |
| `config get\|set <key> [value]` | 读写设置，`--global` 切全局 | P0 |
| `scene list` / `scene open <id>` / `scene close <id>` | 场景管理 | P1 |
| `run [--scene <id>] [--beats N] [--mode auto\|step] [--seed N]` | 跑剧场 | P1 |
| `beat next` / `beat why <seq>` / `beat rewind <seq>` | 单步 / 归因 / 回退到该拍 | P1 |
| `restore --checkpoint <id>` \| `--seq N` \| `--from-commit <sha>` | 检查点与 Git 恢复（开新分支） | P1 |
| `log [--limit N]` | 检查点与提交列表 | P1 |
| `fact list\|add\|supersede\|lock` | 事实与设定锁 | P2 |
| `clue list [--stale]` | 未回收线索（按 `clue_max_age_chapters` 标陈旧） | P2 |
| `search <query>` | 只读检索，输出命中与分数 | P2 |
| `chapter new\|gen\|revise\|approve <id>` | 建章 / 成稿 / 修订 / 审批 | P3 |
| `diff <revA> <revB>` | 章节修订对比 | P3 |
| `audit [--chapter <id>]` | 一致性与伏笔体检 | P3 |
| `import <path> [--dry-run]` | 存量稿导入 | P3 |
| `export --format md\|epub\|docx` | 导出 | P6 |

**`run --offline` 必须可用**：用 stub provider 读 `fixtures/beats/*.json` 跑完整流程——这就是黄金场景回归的入口。

### 10.3 退出码

| 码 | 含义 | 谁消费 |
|---|---|---|
| 0 | 成功 | — |
| 1 | 一般错误（IO / 解析） | — |
| 2 | 用法错误（参数或子命令不存在） | 人工 |
| 3 | **约束拒绝**（`ck_*`），stderr 带约束名 | CI 断言 |
| 4 | 模型 / 网络失败（重试用尽） | 重试脚本 |
| 5 | 需要人工介入（`WAITING_FOR_HUMAN`、越界待裁决） | GUI 唤起 |
| 6 | 预算超限（`budget.stopAt`） | 守卫 |

3 和 5 分开是刻意的：前者"代码拒绝了你"，后者"轮到你了"。CI 只能对 3 断言，对 5 应当挂起等人。

### 10.4 JSON 信封

```json
{"ok":true,"data":{},"warnings":[{"code":"skill_budget","message":"…"}],
 "meta":{"seq":4127,"branch":"main","ms":128}}
{"ok":false,"error":{"code":"constraint","name":"ck_fact_locked","message":"该槽位已被作者锁定"},
 "meta":{}}
```

失败也返回合法信封 + 非零退出码：脚本不需要判两套格式。

## 11. TUI（P4）

TUI 是 CLI 的可视化层，**不含第二套业务逻辑**。它只做三件事：渲染状态、收集按键、把按键翻译成命令。

### 11.1 布局

```
┌─ 长夜将尽 · s17 雨夜·账本 ──────────── 第 12/40 拍 · 冲突 2.1 ─┐
│ 场景                    │ 剧场                                      │
│ ● s17 雨夜·账本  12/40  │ 旁白  雨更大了。檐水连成一道断续的帘……      │
│ ○ s16 客栈·试探  已关闭 │                                          │
│ ○ s15 码头·交接  已关闭 │ 沈昼                                  第9拍│
│                         │ 「你母亲的忌日，快到了吧。」                │
│ Agent                   │ 他把伞收拢，水顺着伞骨滴在门槛上。          │
│  林砚  12  ▮▮▮▮        │ 心理 他在试探我。                          │
│  沈昼   9  ▮▮▮         │ 意图 逼林砚先开口  ⚠ 知识越界·已拦截        │
│  旁白   5  ▮▮          │                                          │
│  祁昭   0  （不在场）    │ 林砚                                  第10拍│
│                         │ 「谁告诉你的。」                          │
├─────────────────────────┴──────────────────────────────────────────┤
│ 单步 视点 林砚  [s]下一拍 [a]自动 [p]指定 [x]收束 [q]退出 [?]帮助    │
└────────────────────────────────────────────────────────────────────┘
```

- 左栏固定 22 列，`Tab` 收起。
- 中栏按**终端显示宽度**换行（CJK 算 2 列），不按字符数。
- 底部状态行常驻，键位提示随上下文变（浏览 / 输入 / 生成中）。

### 11.2 两档尺寸

| 尺寸 | 行为 |
|---|---|
| ≥ 100×30 | 上图三区 |
| 80×24（最小） | 收起左栏，状态行压两行，拍号并入角色行 |

小于 80×24 直接拒绝启动并提示尺寸。**不做"挤一挤"**——挤出来的界面比一句报错更让人困惑。

### 11.3 键位

| 键 | 行为 |
|---|---|
| `s` / `Space` | 下一拍 |
| `a` | 自动跑（再按暂停） |
| `p` | 指定发言（弹出在场角色，回车确认） |
| `x` | 收束当前场景 |
| `r` | 回退到选中拍（确认框列 8 域影响） |
| `w` | 为什么是它（展开 `beat.breakdown`） |
| `i` | 进入输入态（以当前席位发言） |
| `Esc` | 退出输入态 / 中止生成 |
| `Tab` | 收起/展开左栏 |
| `j` / `k`、`↑` / `↓` | 消息间移动 |
| `q` | 退出（有未提交内容时二次确认） |
| `?` | 帮助覆盖层 |

输入态 `Enter` 发送、`Shift+Enter` 换行。**IME 判定与 GUI 共用同一份代码**（`packages/core/ime.ts`），不允许两边各写一份。

### 11.4 颜色与降级

- 默认 256 色，角色色号与 GUI 头像同源。
- `NO_COLOR=1` 或 `--no-color`：只靠字重与缩进区分——旁白用 `│` 竖线，说话人用 `▌`。
- 生成中：状态行右侧 `⠋ 生成中 2.3s  Esc 取消`。不用全屏 spinner，用户要看得到已有内容。

### 11.5 与 GUI 的复用边界

| 复用 | 不复用 |
|---|---|
| 命令总线、上下文装配、限知、回退 | 布局与绘制 |
| IME 判定、键位映射表 | 动画与过渡 |
| 错误码与提示文案 | 富文本渲染 |

「TUI 里出现 `if (tui)` 分支就算失败」这条验收，指的就是这张表：分支只能出现在绘制层，不能出现在业务层。

## 12. 键盘与中文输入法

这是中文桌面应用最容易翻车的地方。

| 键 | 行为 |
|---|---|
| `Enter` | 发送（**仅在非输入法组合态**） |
| `Shift+Enter` | 换行 |
| `Ctrl+Enter` | 强制发送（组合态也发） |
| `Esc` | 中止当前生成 |
| `Ctrl+1/2/3` | 折叠/展开左栏、主区、右栏 |
| `Ctrl+K` | 命令面板 |
| `Space` | 单步模式下：下一拍 |
| `Ctrl+Z` | **只撤销输入框内容**，不撤销已提交的拍（撤销生成请走时间轴） |

IME 判定（必须三选一都做）：

```ts
onKeyDown(e) {
  if (e.nativeEvent.isComposing || e.keyCode === 229) return;  // 组合态
  if (e.key === 'Enter' && !e.shiftKey) send();
}
```

`compositionstart` / `compositionend` 也要跟踪，因为部分输入法在 `compositionend` 后仍会补一个 `keydown`。

**另一个坑**：Safari/WebKit（Electron 在 macOS 上）在中文输入时 `isComposing` 有时为 false。所以 `Ctrl+Enter` 必须永远可用——它是逃生通道。

## 13. 组件树与 IPC

```
<App>
 ├─ <Home>            ProjectCard / NewProjectWizard
 ├─ <Workbench>
 │   ├─ <NavRail>     图标 + 折叠
 │   ├─ <LeftPanel>   SceneList | AgentList | IssueList
 │   ├─ <MainPane>
 │   │   ├─ <Theater>   BeatCard / UserTurn / TheaterBar / WhyThisBeat
 │   │   ├─ <Editor>    CodeMirror6 + 行内批注
 │   │   ├─ <Timeline>  CheckpointList / ImpactPreview / RestoreDialog
 │   │   └─ <Settings>  CharacterEditor / WorldEditor / CardEditor
 │   └─ <RightPanel>  FileTree | Inspector
 └─ <SettingsPage>
```

IPC（主进程 ↔ 渲染进程），全部过 Zod：

```
project:open / project:create / project:close
scene:list / scene:open / scene:pause / scene:resume / scene:close
beat:next / beat:rewind / beat:why / beat:rewrite
turn:submitUser          // 用户扮演时提交
theater:setMode / theater:pickSpeaker
checkpoint:list / checkpoint:preview / checkpoint:restore
git:commit / git:diff / git:log / git:restore
chapter:read / chapter:save / chapter:revise
issue:list / issue:sendToReviser
settings:get / settings:set / provider:test
event:subscribe          // 主进程 → 渲染进程的单向推送
```

**状态管理**：Zustand 五个 store（project / scene / theater / editor / ui）。
所有状态来自主进程推送，渲染进程不做乐观更新——除了输入框。理由：生成一拍有 1–5 秒延迟，乐观更新会让"已提交"和"生成中"混在一起，用户分不清哪条已经进库。

**性能**：
- 对话流虚拟化（`@tanstack/react-virtual`），只渲染可视区 ±10 拍。
- CodeMirror 6 处理 10 万字章节无压力；不要用受控组件同步全文。
- 主进程推送按 `scene_id` 过滤，切场景时退订旧场景，避免后台项目把 CPU 吃满。

## 14. 空态、加载、错误

| 场景 | 处理 |
|---|---|
| 没有任何场景 | 显示"从章纲生成第一个场景"与"手写场景卡"两个入口 |
| 场景已关闭 | 主区变只读，顶部横幅"本场已关闭 · 查看摘要 / 重开 / 从检查点派生" |
| 模型未配置 | 主区盖一层引导卡，"去设置 → 模型"，不报错弹窗 |
| 生成中 | 气泡内显示骨架 + 已用时长 + 取消按钮；超过 30 秒提示"模型响应慢，可以取消重试" |
| 生成失败 | 卡片内联错误 + "重试 / 换模型重试 / 跳过这一拍"；**不吞错** |
| 知识越界被拦 | 黄色高亮 + "已拦截：沈昼不知道 X" + "仍然保留（记为越界）" |
| 数据库版本高 | 拒绝打开 + "此项目由更新版本创建（v3 > v1），请升级" |

## 15. 一张图看清"为什么这么排"

用户在创作时的注意力顺序是：**这一拍写了什么 → 它变成的稿子长什么样 → 这一拍对不对 → 我在哪一章**。

所以四列的分工是：

| 列 | 回答的问题 | 性质 |
|---|---|---|
| 左栏 | 我在哪一章、这一场？谁在场？ | **会变、要点的**（场景、Agent、章节） |
| 剧场（主区） | 这一拍写了什么？ | 最大、最亮、动效都在这里 |
| 正文预览 | 演出来的东西像稿子吗？ | 只读跟随，不抢焦点 |
| 右栏 | 这一拍对不对？（目标/条件/事实/线索/牌堆） | 数值与证据，几乎不写长文本 |

把"文件列表"放在右栏而不是左栏，是因为左栏要放需要频繁点击的导航，右栏放只读的参考。把"正文预览"放在剧场右边而不是右栏，是因为它是**连续的文本**，需要宽度与行高；挤进 248 px 的侧栏会变成不可读的窄条。
