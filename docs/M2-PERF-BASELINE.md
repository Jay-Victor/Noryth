# M2 10 万字性能基线（阶段 23）

> 对应：`docs/PHASE-23-SCALE-100K.md` §5（M2-6）、`docs/DEV-PLAN.md` §13.7 / §11.8 / §5.12、`docs/PRD.md` §9.2
> 测试：`PERF-M2-01`（`tests/perf/m2-scale.spec.ts`）｜报告：`scripts/m2-perf-report.mjs`
> 日期：2026-11-24 ｜ 结论：**全部目标项 PASS；旧 `PERF-01` / `PERF-M1-01` 未退化（检索反而更快）**

## 1 方法

- **100k 夹具**：3 卷 × 10 章 = 30 章，每章 3 场 × 8 拍 = 24 拍，共 720 拍；
  每拍按「章-场-拍-角色」加唯一前缀，五个角色用不同句长 / 口头禅 / 问句率，
  避免全篇同文让 DOCX 压缩率与缓存命中虚高。
- **数据状态**：30 章全部定稿（final revision + 清单 + 章末摘要）、
  3,000 条记忆（2,900 活跃 + 100 软归档，含 200 条可归档重复经历）、
  3,000 条 `memory_vec` + `memory_fts`、90 条 `voice_metric`（30 章 × 3 场）、
  153 条 `turn_metric`（六 Agent + 项目级规划）、12 条伏笔（8 回收 / 4 未回收）。
- **确定性**：夹具是纯函数计划（显式 id、固定时钟、无随机数）；同一 seed 两次生成
  `fixtureDigest` 相同，每拍正文唯一。
- **采样**：预热 3 次、采样 20 次；P95 用最近秩（`ceil(0.95 × n) - 1`）。
  打开口径 = 迁移检查 + `db.verify()` + 章列表摘要（第二个连接等价冷启动），不含模型。
- **命令**：

```bash
pnpm test:perf
node scripts/m2-perf-report.mjs --from out/perf/m2-perf-report.json
```

## 4 查询计数（无 N+1）

用测试包装 `db.prepare` 计数；数字与章数、拍数无关：

| 路径 | 语句数 | 口径 |
|---|---:|---|
| 成本报表（全书） | 8 | 聚合 + 章/纲标题 + 字数 ×2 + 耗时样本 + 事件 |
| 成本报表（单章过滤） | 9 | 只多一次「章存在」校验 |
| 声音指标（单场） | 9 | 场景 / 归属 / 章 / revision / 清单 + 每角色一次角色卡 |
| 归档候选（3k 条） | 8 | 记忆 + 事实 + 边 + pending 提案 + 每角色一次向量批读 |
| 检索（3k 条，top_k 8） | 4 | pinned + vec KNN + FTS + 批量取候选行 |

断言上界：报表 ≤10、声音 ≤12、归档 ≤25、检索 ≤12。若按章或按拍发查询，
30 章时这些数字会直接到 30–720，测试会失败。

## 5 本阶段优化（按测量结果）

1. **向量 KNN 的执行顺序（最大收益）**
   - 现象：3,000 条记忆时单次检索 **P95 1,521ms**（第一阶段测量）。
   - 定位：`EXPLAIN QUERY PLAN` 显示 SQLite 选了
     `memory_own(character_id, status, learned_seq)` 当外循环，再对每条候选记忆
     各跑一次 vec0 全表扫描（600 × 3,000 次距离计算）；KNN 本身只要 1.5ms。
   - 修复：`memory_vec` 与 `memory_entry` 改为 `CROSS JOIN`，固定
     「vec0 先取 k 个最近邻，再按 id 过滤」的执行顺序（与 DEV-PLAN §10.4 一致）。
   - 结果：检索 P95 **1,521ms → 9ms**（约 170×）。
2. **检索候选批取**：`retrieveOwn` 原来对每个候选 `memory.get()`（最多 60 条单行查询），
   改为 `MemoryRepo.listByIds()` 一次 `IN`。`PERF-01`（2,000 条记忆）检索 P95
   从 23–27ms 降到 **3ms**。
3. **归档候选**：文本键按条目缓存（原来每条候选对同组逐条 NFKC 归一化），
   向量按角色一次 `readVectors()` 批量读回（原来逐条 `readVector()`）。
   3,000 条 / 200 个候选的路径稳定在约 30ms、8 条语句。
4. **声音指标**：同一场的角色卡按 id 缓存，24 拍不再逐拍 `character.get()`；
   单场 9 条语句（原为 24+ 条）。
5. **UI 分页**：记忆浏览器与「维护 → 已归档」列表每页 50 行
   （`shared/domain/pagination.ts`，纯函数单测覆盖 3,000 行；筛选变化回到第 1 页）；
   成本报表 100+ 行沿用 `VirtualList`（阶段 20 已接）。
6. **迁移 0015 未使用**：`EXPLAIN` 显示瓶颈是执行顺序与查询次数，不是缺索引；
   按阶段约定**不新增索引、不加表**，`LATEST_SCHEMA_VERSION` 保持 **14**。

## 7 局限

- 夹具是**合成**的 10 万字项目：文本可读且每拍唯一，但不是真实稿件；
  记忆重复率、群戏人数与成本行按 M2 目标场景设定。
- RSS 是 Node perf 进程的 `process.memoryUsage().rss`，不等于 Electron
  主进程 + 渲染进程 + GPU 的私有工作集合；阶段 24 的 100k 长跑用
  `app.getAppMetrics()` 复测（`E2E-M2-A`）。
- 打开口径在测试进程内跑（迁移 + `db.verify()` + 摘要），不含 Electron 窗口创建；
  `PERF-01` 的历史口径相同，可纵向对比。
- 性能门只在 `pnpm test:perf` / nightly 跑；共享 runner 的磁盘与杀软抖动会让
  墙钟断言不稳定，提交门只跑功能 E2E。
- 声音指标用夹具文本计算（五角色句长/口头禅不同），不代表真实项目的区分度；
  真实语料基线见 `docs/M2-METRICS-BASELINE.md`。
- 检索向量的 `k=30` 是**全局**最近邻再按角色过滤（DEV-PLAN §10.4 原口径）；
  角色数很多时单角色召回会变少，关键词通道兜底。若未来角色数显著增加，
  再评估 `k` 或分区索引（需要迁移，不在本阶段范围）。
- 记忆台 `memory.state` 仍一次返回项目全部记忆行（3,000 条约 1.5MB IPC），
  列表本身已按 50 行分页渲染；若后续要压缩 IPC 体积，再把过滤/分页下推到
  主进程（会改 `memory.state` 契约，不在本阶段范围）。
